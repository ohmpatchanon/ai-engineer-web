## จาก chain ไปถึง agent: เส้นแบ่งบางมาก

workflow คือลำดับการทำงานที่มนุษย์กำหนดตายตัว โดยแต่ละขั้นจะส่งผลต่อกันไม่ว่าจะเป็นแบบ chain หรือ router ที่เลือกตามเงื่อนไขที่กำหนดไว้ ส่วน agent คือระบบที่ให้โมเดลตัดสินใจเองว่าควรเรียก tool ใดเมื่อไร การตัดสินใจเช่นนี้เป็นการกำหนด autonomy ขั้นตอนการทำงาน โดยการตัดสินใจเหล่านี้ต้องมีเหตุผลที่ชัดเจนและวัดได้
หลัก ReAct ผูกการคิดถึงการกระทำไว้เป็นลำดับที่สลับกันซึ่งเรียกว่า ReAct loop โดย Reason คือการคิดว่าต้องทำอะไรและ Action คือการเรียก tool หรือการตอบ การวนแบบนี้ดำเนินไปจนกระทั่งเงื่อนไขจบได้รับการกระตุ้น มุมมองนี้เปิดโอกาสให้โมเดลทำตามเป้าหมายได้อัตโนมัติ
ขั้นตอนที่สำคัญคือการตรวจสอบได้ว่าการทำงานสำเร็จหรือไม่ เมื่อโมเดลสามารถเรียก tool อัตโนมัติแล้วส่วนการประเมินผลนั้นก็ต้องเป็นส่วนหนึ่งของระบบด้วย จึงจะยืนยันได้ว่า autonomy ที่เพิ่มขึ้นไม่ได้ไปเบียดเบียนความปลอดภัยและคุณภาพของระบบ
นี่คือจุดที่ autonomy มากขึ้นเป็นต้นทุนและความเสี่ยงที่เพิ่มขึ้น ไม่ใช่ผลดีโดยอัตโนมัติ จึงควรเริ่มจากสิ่งที่ง่ายที่สุดและวัดผลได้ก่อนแทนการเชื่อว่า autonomy จะเป็นคำตอบของทุกอย่าง
> [!DEFAULT]
> เริ่มจาก workflow ที่ตายตัว/กำหนดได้ ก่อนยอม autonomy: chain → router → agent โดยปล่อย "ลูบ" ทีละชั้นเฉพาะเมื่อวัดแล้วว่าจำเป็นจริง

## ReAct loop และ step limit

ReAct คือการผลัดกัน Reason และ Action อย่างเป็นจังหวะ โดย Reason ทำการวางแผนว่าต้องทำอะไรต่อไปและ Action ทำการเรียก tool หรือตอบเมื่อแผนชัดเจน วนไปเรื่อย ๆ จนเงื่อนไขจบครบ นั่นคือวงของ ReAct ที่อธิบายการทำงานของ agent ได้ชัดเจน
เหตุผลที่ต้องจำกัด steps ไว้ให้ชัดคือการทำให้ระบบไม่เกิดการวนและเผาต้นทุนโดยเปล่าประโยชน์ เพราะไม่มีกำหนดเงื่อนไขจบที่ชัดเจนโมเดลอาจวนทำซ้ำ ยี่สิบรอบและเสียทรัพยากรที่เกินไปโดยไม่ให้ผลตอบที่เป็นประโยชน์
การหยุดนั้นไม่ใช่เพียงการกำหนดตัวเลข แต่เป็นเงื่อนไขที่ทำให้ระบบรู้ว่าเมื่อไรจะหยุด ดังนั้นการกำหนดเงื่อนไขจบ เช่น เงื่อนไข step limit หรือเกณฑ์จบ ต้องเป็นส่วนหนึ่งของทางเลือก และต้องชัดเจนเพียงพอที่โมเดลจะรู้ว่าเวลาที่จะจบคือเมื่อไร

*Agent loop (ReAct) — Plan → Act (tool_call) → Observe → Reflect วนจน done / ชน step-limit / error — tool ต้องผ่าน schema, validate, timeout และ log ทุกครั้ง*

## tool calling: schema คือ API ของ agent

เครื่องมือต้องประกาศเป็น schema ที่ชัดเจน ทั้งชื่อ description ข้อความบอกว่าเมื่อไรควรเรียกใช้ และรายละเอียดของพารามิเตอร์เพื่อให้โมเดลสามารถเลือก tool และอาร์กิวเมนต์ได้อย่างถูกต้อง การเขียน description ที่คลุมเครือทำให้ agent เรียก tool ผิดหรือไม่ก็เรียก tool หลายตัวที่มีความซ้ำซ้อนกัน
เมื่อมีการเรียก tool แล้วต้อง validate อาร์กิวเมนต์ก่อน execution ตาม schema และกำหนด timeout และจำนวนการทำซ้ำไว้ล่วงหน้า และเมื่อผล tool คือ exception ต้องแปลงเป็น observation ที่ทำให้โมเดลสามารถจัดการได้ถูกต้องและไม่ทำให้ loop หยุดทำงาน
การ log ทุก tool call คือการบันทึก tool, args, latency และ result ไว้ทุกครั้งเพื่อใช้สำหรับประโยชน์ในภายหลังและสำหรับการ debug และการตรวจย้อนกลับที่จำเป็น ซึ่งเป็นการลงมือทำอย่างถูกต้องโดยไม่กลายเป็นบาป
เหตุผลที่ต้อง log ทุก call คือการทำให้ระบบมีหลักฐานของข้อมูลเพื่อตรวจสอบและประเมินได้อย่างครบถ้วน เมื่อเรียก tool แล้วต้องให้ผลลัพธ์ที่เป็นรูปธรรมเพื่อให้โมเดลนำไปตัดสินใจได้
```json
{ "name": "query_orders",
  "description": "ค้นหาสถานะคำสั่งซื้อด้วย order_id ใช้เมื่อผู้ใช้ถามเรื่องคำสั่งซื้อ",
  "parameters": {
    "type": "object",
    "properties": { "order_id": { "type": "string" } },
    "required": ["order_id"] } }
```

## memory, context และการปกป้องข้อมูล

Agent ที่คุยหลายรอบต้องมีช่องทางในการจำและจัดการข้อมูล การจำแบบ stateless คือการย่อประวัติล่าสุดเข้า prompt ซึ่งต้องการการบริหารบริบทเช่นการเลือกว่าจะเก็บส่วนไหนและการยัดบริบทให้เหมาะสมและการตัดเนื้อหาที่เกินไป ดังนั้นการเก็บทั้งหมดอาจทำให้เปลือง token และสับสนในการตอบ
การจำแบบ persistent คือการสรุปความก้าวหน้าให้สั้นและเก็บไว้ใน store ซึ่งทำให้ระบบจำได้อย่างคงที่และไม่เปลืองโดยไม่จำเป็นและการย่นย่อให้สั้นและเป็น bullet สั้น ๆ ตามรอบจะทำให้การทำงานของ agent สะดวกและเร็วขึ้นมาก
การเก็บ note เพราะข้อมูลเหล่านี้เป็นเรื่องการปกป้องข้อมูลที่มีประสิทธิภาพและความปลอดภัยจะต้องคำนึงถึง โดยอนุญาตให้ tool ที่จะเรียกได้จะต้องกำหนดให้อยู่ใน allowlist และต้องกำหนดขั้นตอนที่เสี่ยงเป็น human-in-the-loop อย่างชัดเจนในทุกขั้นตอนและไม่ให้โมเดลทำงานเกินขอบเขตโดยไม่ได้รับอนุญาต

## guardrails: ความปลอดภัยเป็นสถาปัตยกรรม ไม่ใช่คำสั่ง

ความปลอดภัยในงาน agent ต้องเป็นในลักษณะสถาปัตยกรรมไม่ใช่เพียงคำสั่งใน prompt เพราะโมเดลอาจรั่วหรือคล้อยตาม prompt ที่ผู้ใช้ไม่ต้องการให้ทำ วิธีที่มีประสิทธิภาพกว่าคือ not ใส่คำสั่งใน prompt แต่ทำให้เป็นส่วนหนึ่งของระบบเช่น�ารกำหนด allowlist ของ tool ตามบทบาทผู้ใช้
ขั้นตอนที่ทำลายข้อมูลอย่างลบ ส่งข้อมูลออก หรือเขียนทับจะต้องมี human-in-the-loop อนุมัติทุกครั้งก่อนดำเนินการ เพราะจะปกป้องข้อมูลสำคัญและทำให้ผู้ใช้ควบคุมระบบได้อย่างรัดกุม ซึ่งหมายถึงการสร้างสถาปัตยกรรมกู้คืนให้ระบบได้อีกทางหนึ่ง
จากมุมมองนี้ทำให้เห็นว่าความปลอดภัยเป็นส่วนหนึ่งของการออกแบบ pipeline โดยต้องใส่ guardrails ในทุกขั้นที่มีการเรียก tool หรือมีการตัดสินใจที่มีผลเสียหาย นี่คือการประกันว่าระบบ agent ไม่หลุดจากขอบเขตและยังควบคุมได้แม้โมเดลจะทำตามคำสั่งได้แม่นยำแล้วก็ตาม

## ประเมิน agent: ดู trace ไม่ใช่ดูคำตอบสุดท้าย

Metric สำหรับ agent คือ task success rate, steps เฉลี่ย, tool error rate ต้นทุนต่องานและจำนวน failure modes เช่น การเรียก tool ผิด การเก็บ args ผิด วน loop และการหยุดก่อนที่จะจบ วิธีนี้ทำให้เราเห็นภาพของสิ่งที่ผิดได้ชัดเจนและเข้าใจว่าการทำงานของ agent พร้อมต่อยอดหรือไม่
การสร้างชุดเคส 30 ถึง 50 งานพร้อม golden response ช่วยให้เราวัดได้ว่า agent ทำงานได้ดีเพียงใดในแต่ละ task และเหตุผลที่ต้องมี golden response คือการทำให้เราวัดได้ว่า agent ทำถูกกฎจริงหรือไม่ มือออกแบบจึงต้องมีหลักเกณฑ์ประเมินไว้ก่อน
หัวใจของการ debug agent คือการอ่าน trace ที่บันทึกลำดับคำถามและลำดับการทำงานทั้งหมดตั้งแต่ query ผ่าน reasoning การเรียก tool การ observe และกลับไปตัดสินใจใหม่จนจบ การทบทวนและตรวจ trace ในแต่ละสัปดาห์จะช่วยให้เราปรับงานได้จริงของระบบ agent
เหตุผลที่ต้องทำอย่างสม่ำเสมอคือตัวเลขเฉลี่ยซ่อนรายละเอียดที่มันแสดง ว่าในงานที่ดูดีนั้นอาจซ่อนข้อบกพร่องบางส่วน และการทบทวน trace ช่วยให้เรารู้ได้จริงว่า agent กำลังทำอะไรและทำไมถึงต้องปรับ
