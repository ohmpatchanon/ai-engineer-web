## จากข้อความสู่ตัวเลข: ลำดับขั้นตอนที่ต้องรู้

โมเดลภาษาไม่ได้อ่านตัวอักษรตรง ๆ แต่ต้องแปลงข้อความดิบก่อนเสมอ ขั้นตอนเริ่มต้นคือการ normalize เช่น รวมพิมพ์เล็กพิมพ์ใหญ่และรูปแบบช่องว่าง หลังจากนั้นจึงแยกเป็นหน่วยเล็ก ๆ ที่เรียกว่า token แล้วย้อนกลับกับ vocab เพื่อระบุ id ของแต่ละหน่วย
หลังจากได้ id แล้วระบบจึงเปลี่ยน id เป็น vector ที่เรียกว่า embedding ซึ่งมีความยาวคงที่และพร้อมเข้าโมเดลต่อไป ลำดับนี้สำคัญมากเพราะหากขั้นตอนแรกผิด การฝืนแปลค่าเข้าโมเดลจะไม่ช่วยแก้ปัญหาอะไรได้ ข้อผิดพลาดจึงมักมาจากการมองข้ามการ normalize มากกว่าอาการฝืนใจในการประมวลผล
ความผิดพลาดของระบบ tokenizer ต้องถูกวัดบนข้อความจริงไม่ใช่ข้อความทดสอบ เพราะประโยคภาษาไทยและข้อความภาษาอังกฤษมีพฤติกรรมแตกต่างกันโดยมากทั้งในด้านการตัดคำและสัญญาณพิเศษ โมเดลที่รองรับ vocabulary ไม่เหมาะกับข้อความจริงจะมีผลลัพธ์ผิดแม้โมเดลจะมีสถาปัตยกรรมที่ดี

## bag-of-words และข้อจำกัดที่ทำให้ต้องมี dense embedding

วิธีดั้งเดิมในการเปลี่ยนข้อความเป็น vector คือ bag-of-words ซึ่งทำข้อความให้เป็นตัวเลขนับความถี่ของแต่ละคำในคำทำทั้งหมด ตัวอย่างเช่นข้อความที่มีคำว่า แมว 3 ครั้ง คำว่า บาท 1 ครั้ง จะถูกแปลงเป็น vector ที่มีค่า 3 ในตำแหน่งของคำว่า แมว และ 1 ในตำแหน่งของคำว่า บาท
วิธีนี้ทำให้ feature แทนเรื่องที่เกิดขึ้นด้วยความทำหน้าซ้ำโดยไม่รู้ลำดับของข้อความ จึงแยกข้อความที่มีคำเดียวกันแต่เรียงลำดับต่างกันไม่ได้ และเมื่อ vocabulary ขนาดหลายหมื่นคำ vector จะมีสมาชิกจำนวนมากที่เป็นศูนย์ ทำให้การคำนวณความคล้ายช้าและเปลืองพื้นที่
ข้อจำกัดที่สำคัญที่สุดคือ bag-of-words ไม่สามารถทำให้คำพ้องความหมายอยู่ใกล้กันจึงไม่รู้ความหมายได้ดี ระบบจึงต้องไปสู่ dense embedding ที่ทำให้หลายคำที่อยู่ร่วมกับบริบทเดียวกันมีค่า vector ใกล้กัน ซึ่งใช้ประโยชน์จากข้อเท็จจริงเชิงสถิติว่าพฤติกรรมบริบทสะท้อนความหมาย

## distributional hypothesis และ word2vec

หลัก distributional hypothesis กล่าวว่า คำที่มีบริบทคล้ายคลึงมักมีความหมายคล้ายคลึงกัน หลักการนี้แม้ฟังดู simplicity แต่มีความหมายลึกเบื้องหลังคือการใช้ประโยชน์จากการเกิดร่วมกันของคำในข้อความจำนวนมากเพื่อสร้างความหมายเชิงสถิติ วิธี word2vec จึงอาศัยการทำนายบริบทหรือทำนายคำจากบริบทเพื่อสร้าง embedding ที่สะท้อนความสัมพันธ์เหล่านั้น
คุณสมบัติที่ได้รับความสนใจมากที่สุดคือความสามารถในการทำการคำนวณ vector เชิงเรขาคณิต เช่น king ลบ man บวก woman ให้ผลใกล้กับ queen ปรากฏการณ์นี้ทำให้เห็นว่า embedding เก็บความแตกต่างเชิงความหมายไว้ในทิศของ vector ไม่ใช่เพียงความใกล้ของคำโดยตรง แต่สะท้อนความหมายหลายมิติอย่างเป็นระบบ
นั่นไม่ได้หมายความว่า word2vec รู้ความหมายของคำอย่างมนุษย์ แต่หมายความว่ามันทำเป็นตัวเลขที่มีประโยชน์มากมายสำหรับการค้นและความเทียบเคียง ข้อจำกัดคือคำหนึ่งได้ vector ชุดเดียวทั้ง ๆ ที่คำเดียวกันอาจใช้ในหลายบริบทที่ต่างกันมาก การสร้างบริบทเชิงลึกเป็นข้อจำกัดที่ Transformer แก้ไขในภายหลัง
### สูตร: analogical arithmetic ของ word2vec

king − man + woman ≈ queen   (vector เกิดจากคำนวณค่าความหมายเชิงเรขาคณิตของ embedding)

> vector ได้มาจากการคำนวณผลรวมของ vector ที่สะท้อนความหมายเชิงทิศทาง ไม่ใช่การคำนวณเชิงพจนานุกรม

## subword tokenization (BPE): วิธีที่ LLM แก้ OOV

การแยกเป็นคำเต็ม ๆ ไม่สามารถรองรับคำที่เพิ่งพบได้เสมอไป เรียกว่า OOV (out-of-vocabulary) แต่ Byte-Pair Encoding หรือ BPE แก้ปัญหานี้โดยเริ่มจากหน่วยอักขระและรวมคู่ที่เกิดบ่อยที่สุดให้เป็นหน่วยกลางทีละขั้น ระบบจึงได้ทั้ง vocab ขนาดคงที่และสามารถครอบคลุมคำใหม่ได้อย่างเป็นธรรม
หน่วยย่อยที่ได้มาเช่น un- หรือ -ed แชร์ส่วนของความหมายร่วมกันระหว่างหลายคำซึ่งช่วยให้โมเดลสามารถเรียนรู้การประกอบหน่วยได้ดีกว่าการจำเป็นคำชุดเดียวทั้งหมด กลไกนี้ทำให้ภาษาไทยใช้หลาย token ต่อหนึ่งคำเนื่องจากโครงสร้างภาษาไทยเป็น abugida ต่างจากภาษาอังกฤษ
ผลสืบเนื่องจากการแยก token นี้คือจำนวน token ไม่เท่ากับจำนวนคำ และอาจมีผลต่อต้นทุนและ context window โมเดลโฆษณาว่า context window ขนาด 128k หมายถึง 128k token ไม่ใช่ 128k คำ จึงต้องคำนวณ token ต่อข้อความเมื่อออกแบบต้นทุนและขอบเขตของระบบ

## embedding แบบ dense กับความคล้ายเชิงทิศทาง

Dense embedding เป็น vector ที่มีค่าจริงทุกมิติและไม่ได้เป็นศูนย์ในหลายช่องเหมือน bag-of-words ทำให้สามารถเปรียบเทียบได้ด้วย cosine similarity และ Euclidean distance การวัดความคล้ายนี้อาศัยมุมระหว่าง vector และระยะห่างของจุด ในงานค้นคืนเราจะวัดทิศทางของความหมายมากกว่าระยะห่างของตัวเลขทั้งหมด
การมี vector หลายร้อยมิติทำให้คำที่มีความหมายใกล้เคียงมีเวกเตอร์ทิศทางใกล้กัน และเครื่องมือใน vector database เก่งกับการสืบค้นเชิงทิศทางนี้ได้เร็วกว่ามาก นี่คือเหตุผลที่ embedding model เป็นเทคโนโลยีหลักของงานค้นคืนเชิงความหมายในปัจจุบัน ไม่ใช่เพียงตัวเสริมของระบบค้นหาแบบดั้งเดิม
ผู้ใช้ต้องเลือก embedding model ให้เหมาะกับงานจริง เพราะ embedding ที่ฝึกมาในสไตล์ทั่วไปอาจเข้าใจภาษาไทยไม่ดีพอสำหรับศัพท์เฉพาะในโดเมนพิเศษของคุณ การวัดผลบนชุดทดสอบจริงเป็นวิธีที่ต้องทำก่อนตัดสินใจเทียบกับผลทดสอบจากคู่มือทั่วไป
> [!KEY INSIGHT]
> Embedding ไม่ได้ "รู้ความหมาย" — มันจับรูปแบบการเกิดร่วม (co-occurrence) ในข้อมูลมหาศาลแล้วบีบเป็นตัวเลขที่ใช้หาความคล้ายเชิงทิศทางได้

## vector ของประโยค/เอกสาร: pooling กับวิธีที่อิงหลักฐาน

งาน retrieval และการค้นคืนเชิงความหมายมักต้องการ vector ชุดเดียวต่อข้อความระดับประโยคหรือเอกสาร แทนที่จะใช้ประโยคทั้งเส้นตรง ๆ เราจึงต้องสรุป sequence หลาย token ให้เหลือ vector สำหรับค้นหา วิธีธรรมดาคือการเฉลี่ย embedding ของทุก token ในประโยค ซึ่งให้ผลพอใช้ได้แต่ค่อนข้างหยาบเพราะทุก token มีน้ำหนักเท่ากัน
วิธีที่ดีกว่าคือใช้โมเดลที่ฝึกด้วย contrastive objective ซึ่งทำการเปรียบเทียบคู่เอกสารเพื่อผลักให้เอกสารที่ใกล้เคียงเชิงความหมายอยู่ใกล้กัน และเอกสารที่ไม่ใกล้ให้อยู่ไกลกัน นั่นทำให้การค้นคืนแม่นมากกว่ารู้จักความหมายโดยเฉลี่ย
เมื่อเลือก embedding model ต้องวัดด้วยชุดคำถามและเอกสารจริงของคุณเพราะศัพท์เฉพาะใน domainของคุณเองทำให้ระยะทางใน space ต่างจาก domain อื่น อย่าเพิ่งเชื่อคะแนน leaderboard ทั่วไปก่อนทดสอบกับข้อความของคุณเอง
