## โมเดลคือฟังก์ชันและวงจรเทรนสี่จังหวะ

โมเดล ML ทุกแบบ สรุปแล้วคือฟังก์ชันคณิตศาสตร์แบบเดียวกัน: รับ input, คูณด้วย weight, ผ่าน activation แล้วปล่อย prediction สิ่งที่ training ทำคือเลือกค่าของ weight ทั้งหมดให้ prediction ตรงกับคำตอบจริงมากที่สุด ขั้นตอนเทรนคือวงจรสี่จังหวะ: forward (คำนวณคำตอบ), loss (วัดผิดแค่ไหน), backward (หา gradient = แต่ละ weight ควรขยับไปทิศไหน), update (ขยับ weight ตาม learning rate) แล้ววนซ้ำเป็นหมื่นครั้ง
forward pass คือการเดินข้อมูลจากซ้ายไปขวาผ่าน linear layer และ activation ทุกชั้น จนได้ตัวเลขปลายสุดท้าย เช่น โมเดลจำแนกสุนัขจะปล่อยความน่าจะเป็นสามคลาสรวมกันได้ 1 ภายใน forward ไม่มี learning เกิดขึ้นเลย มันคือการคำนวณเท่านั้น รายการ weight ทำหน้าที่เป็น "ครั้งคราวน้ำหนัก" ของแต่ละสัญญาณ และคำตอบจะดีหรือไม่ดีขึ้นอยู่กับ weight เหล่านั้นเท่านั้น
backward pass คือการเริ่มจาก loss แล้วสืบย้อนกลับไปว่าตั้งแต่ต้นจนจบ แต่ละพารามิเตอร์ส่งผลต่อ loss แค่ไหน ตัวเลขนี้คือ gradient ของ loss เทียบกับพารามิเตอร์ตัวนั้น เป็นสิ่งที่ backpropagation คำนวณอย่างเป็นระบบด้วย chain rule ความน่าแปลกใจของวงจรนี้คือ ตัวเลขที่เสียน้อยที่สุดสำหรับพารามิเตอร์หลายล้านตัวก็ยังถูกคำนวณครบในรอบเดียว ไม่ต้องเดาทีละตัว
update คือการขยับทุกพารามิเตอร์พร้อมกันด้วยขนาดก้าว eta (learning rate) ผสมกับทิศทางของ gradient ถ้าก้าวใหญ่เกินจะกระโดดข้ามหุบของ loss ก้าวเล็กเกินจะคืบช้า การขยับพารามิเตอร์แบบนี้ซ้ำ ๆ จึงไม่ใช่ "การจำ" แต่เป็นการค่อย ๆ วางรูปของฟังก์ชันให้ตรงกับข้อมูลที่สุดจากมุมคณิตศาสตร์
การเทรน "ได้ผล" ไม่ได้แปลว่า loss ลดเป็น 0 — แปลว่าโมเดลสร้างกฎที่ generalize ไปยังข้อมูลใหม่ได้ นี่คือประเด็นที่แยกวิศวกร ML ที่ดีออกจากคนที่แค่ทำให้ loss ลงได้ เพราะ loss ขนาด train ต่ำเพราะ overfitting สวยชัดเจนกว่าจริง แต่ไม่มีประโยชน์ในโลกจริง
trade-off หลักของวงจรนี้คือ โมเดลที่ใหญ่มาก (พารามิเตอร์หลายล้าน) เรียนรู้ได้เร็วกว่าและครบกว่า แต่ใช้เมมโมรีกับการคำนวณระดับใหญ่ การฝึกทีละตัวอย่าง (SGD) กระเทือนมากและจูนง่าย แต่ใช้เวลาเกินไป ส่วน batch ใหญ่ทำให้ gradient นิ่งแต่ต้องวัดรอบทิศให้ดี วิธีฝึกที่ดีคือผูกตัวเลขทุกตัวในวงจรเข้ากับผลบน validation ไม่ใช่เลือกเพราะดูเท่
### สูตร: วงจรการเทรนในหนึ่งบรรทัด

θ ← θ − η · ∇loss(θ)   (θ = พารามิเตอร์, η = learning rate, ∇loss = gradient)

> ปรับพารามิเตอร์ไปทิศทางตรงข้าม gradient ด้วยขนาดก้าว η — ซ้ำจน loss บรรจบ (converge). ถ้าเห็น loss ลดช้า อย่าโทษโมเดลก่อน ลองดู eta และส่งข้อมูลขนาดเท่าไร
```python
# วงจรเทรนพื้นฐาน (1 epoch คือการเห็นข้อมูลฝึกครบ 1 รอบ)
import numpy as np

theta = np.array([0.0, 0.0])      # พารามิเตอร์เริ่มต้น
lr = 0.01                          # learning rate

for step in range(1000):
    pred = theta[0] * X + theta[1]   # forward: คำนวณคำตอบ
    loss = np.mean((pred - y) ** 2)  # loss: วัดความผิด
    # backward: derivative ของ MSE เทียบกับ theta
    grad0 = np.mean(2 * (pred - y) * X)
    grad1 = np.mean(2 * (pred - y))
    theta = theta - lr * np.array([grad0, grad1])  # update
    if step % 200 == 0:
        print(f'step {step} loss {loss:.4f}')
```

## ความผิดที่วัดด้วย loss ไม่ใช่แค่ถูก/ผิด: softmax, cross-entropy, MSE

งาน classification ไม่ได้ให้ "ถูก/ผิด" แต่ให้คะแนนความมั่นใจในทุกคลาส (logit) จากนั้น softmax เปลี่ยนคะแนนให้เป็นความน่าจะเป็นที่รวมกันได้ 1 เราวัดความผิดด้วย cross-entropy: ยิ่งความน่าจะเป็นของคำตอบจริงต่ำ ค่า loss ยิ่งสูงแบบไม่เป็นเส้นตรง — โมเดลจึงถูก "บังคับ" ให้มั่นใจมากขึ้นเรื่อย ๆ ไม่ใช่แค่พอเดาถูก
ตัวอย่างเป็นภาพคือ เดาสุ่มทั้งสามคลาสเท่า ๆ กันได้ cross-entropy ประมาณ 1.1, เดาแม่น 70% ได้ loss น้อยกว่า, แต่เดามั่นใจและผิด (เช่น ตอบคลาส A 90% ทั้งที่จริงคือคลาส B) จะโดนลงโทษหนักมาก ไม่ใช่แค่พลาดเปียก ๆ เพราะโมเดลควรเชื่อน้อยลงเมื่อผิดจริงทันที การลงโทษแบบ log นี้ทำให้โมเดลที่ "กล้าผิดด้วยความมั่นใจ" ถูกหักคะแนนหนักกว่าโมเดลที่ลังเล
สาเหตุที่ใช้ cross-entropy ไม่ใช่ MSE (mean squared error) สำหรับ classification คือ MSE กับ softmax เข้ากันไม่ดีในทาง gradient เพราะ MSE พอค่าความมั่นใจสูงเกินจะอิ่มตัวและ gradient จ่อลงเร็วจนค่อย ๆ ไม่เรียนรู้ ส่วน cross-entropy กลไกผลักคะแนนคลาสถูกให้ขึ้นคลาสอื่นให้ลงตลอดโดยไม่ต้องพึ่งขนาดค่ากำลังสองขนาดใหญ่
ใน regression เรากลับใช้ MSE เพราะต้องการวัดระยะทางจริงระหว่างค่าที่ทำนายกับค่าจริง ถ้าค่าจริงคือ 100 และทำนาย 90 แทน 80 อันหลังผิดกว่าและต้องลงโทษแรงกว่า linear แบบกำลังสอง เพราะโทษเรื่องขนาดความผิดไม่ใช่แค่ทิศทาง งานที่วัดเป็นตัวเลขต่อกันจึงใช้ MSE/MAE ซึ่งค่าสัมบูรณ์เฉลี่ยของความผิดแบบเป็นเส้นตรงและทนทานต่อ outlier มากกว่าในทางสถิติ
trade-off ที่ต้องเห็นคือ loss เลือกได้เหมาะสมกับงานก็ยังมีข้อเสียแค่นานา loss เอาแต่ค่าจริงในคลาสเดียวมาลงโทษ ทั้งที่ในงานจริงอาจผิดคนละคลาสแต่ความอันตรายไม่เท่ากัน เช่น คลุมโรคหัวใจกับคลุมเป็นหวัด ผิดคนละเรื่องกัน ไม่มี loss ใดสร้างต้นทุนทางสมองให้ครบทุกกรณี ต้องออกแบบ metric ตัดสินใจแยกต่างหาก และใช้ loss เป็น GPS ในการเทรนหลักที่ยอมความคลาดเคลื่อนได้บางส่วน
### สูตร: Cross-entropy, MSE และ MAE

CE = −Σ yᵢ × log(pᵢ)   |   MSE = (1/n) Σ (ŷ − y)²   |   MAE = (1/n) Σ |ŷ − y|

> yᵢ=1 คือคลาสถูก, pᵢ=ความน่าจะเป็นที่โมเดลให้คลาสนั้น, ŷ=ค่าที่ทำนาย, y=ค่าจริง — CE ลงโทษความมั่นใจผิดแบบ log, MSE ลงโทษความผิดใหญ่แบบกำลังสอง, MAE ให้ความอดทนต่อข้อมูลผิดปกติ (outlier) มากกว่า
**ตัวอย่าง — เลขเพื่อสัมผัสความลงโทษ**

โมเดลตอบคลาสถูกด้วยความน่าจะเป็น 0.9 → CE = -log(0.9) ≈ 0.11, ตอบคลาสถูกแค่ 0.1 → CE = -log(0.1) ≈ 2.3, ถ้าตอบคลาสผิดด้วย 0.9 และคลาสถูกแค่ 0.05 → CE จะพุ่งถึง 3 กว่า ดังนั้นโมเดลที่ตอบมั่นใจแต่ยังผิดจะถูกลงโทษหนักที่สุด และนี่คือเหตุผลที่ cross-entropy ฝึกให้โมเดล "รู้ตัว" ว่าอย่ามั่นใจเกิน
> [!WHY NOT MSE?]
> ลองนึกว่าตอบ 0.7 แล้วคำตอบจริงคือ 1: MSE ลงโทษแบบกำลังสอง (0.09) แต่ cross-entropy ลงโทษแบบ log ที่แหลมกว่ามากเมื่อความมั่นใจต่ำในคลาสที่ถูก — จึงผลักโมเดลให้กล้าตัดสินใจได้ดีกว่าในงานจัดหมวดหมู่

## optimizer, batch size และ learning rate: จังหวะของก้าว

gradient descent ขนาดเล็ก (SGD) แก้ทิศตามตัวอย่างทีละตัวและ noisy มาก แต่ช่วยหลุดจากหุบเขาเล็กได้ง่าย ส่วน batch size กลาง ๆ (เช่น 32-256) เป็นอมของสองค่าคือเทรนไวและมั่นคง batch ใหญ่มองทิศทางรวมชัดเจนและคำนวณบน GPU ได้คุ้ม แต่ต้องใช้ learning rate ใหญ่และอาจติดอยู่ในจุดที่ราบเรียบที่ loss น้อยเฉพาะที่ (local minimum) มากกว่าตามสัดส่วน
momentum ช่วยให้ gradient descent ไม่สั่นไปมาตามเสียงของข้อมูล แต่ดัดก้าวตรงไปตรงมาเมื่อทิศทางยาว ๆ เหมือนลูกกลิ้งที่ได้เริ่มกลิ้งแล้วจะพยายามกลิ้งต่อ ส่วน Adam ทำหน้าที่ปรับ learning rate แยกกันทุกมิติของพารามิเตอร์ตามค่าเฉลี่ยของขนาด gradient ทำให้มิติที่ gradient เล็กไม่ถูกกลื่นโดยมิติที่ใหญ่ ทักษะเหล่านี้ไม่เปลี่ยน loss ในที่สุดก็ตาม แต่เปลี่ยนว่าโมเดลจะ convergent ได้เร็วและเสถียรเพียงไร
learning rate scheduling คือการเปลี่ยน eta ตามเวลา เช่น ค่อย ๆ ลดลงเมื่อใกล้ convergence ช่วยให้โมเดลลงจอดนุ่มในหุบของ loss แทนที่จะกระเทือนไปมา ถ้าไม่ลดเลย โมเดลอาจค้างอยู่ตรงขอบหุบโดยไม่ลงลึกพอ การปรับ lr ในหลายรูปแบบ (เช่น warmup ช่วงแรกเพิ่มค่าค่อย ๆ ขึ้น) จึงเป็นวิธีทั่วไปที่ลดความสั่นช่วงเริ่มต้นและเพิ่มประสิทธิภาพเทรน
trade-off ของค่า these นี้คือ จูนตรง ๆ ให้เหมาะกับข้อมูลแต่ละชุดไม่ใช่เรื่องยากแต่ก็ไม่มีค่ามาตรฐานตายตัว lr ที่เหมาะกับข้อมูล 10,000 ตัวอย่างไม่จำเป็นต้องเหมาะกับข้อมูล 1 ล้านตัวอย่าง หลักที่ดีคือเริ่มจากค่ามาตรฐานทั่วไป (เช่น lr 1e-3 สำหรับ Adam) แล้ววัด validation ซ้ำ ไม่ใช่ตามธรรมเนียมว่า "ใช้ค่านี้ทุกโมเดล"
นอกจาก opti, batch size และการตั้ง lr ยังมีเรื่องความมั่นคงเช่น gradient clipping เพื่อตัด gradient ที่ระเบิดและ bf16/gradient accumulation ในโมเดลใหญ่ ซึ่งทั้งหมดมุ่งไปที่จุดเดียวกัน: ปรับจังหวะและความมั่นคงของก้าวให้สอดคล้องกับรูปของ loss landscape ไม่ใช่ตามชื่อสูตร
- SGD: รับตัวอย่างน้อย, ก้าวสั่นมาก, ใช้หน่วยความจำน้อย
- momentum / Adam: เสียน้อยลงแต่สอนเร็วและเสถียรเมื่อมิติ gradient ไม่เท่ากัน — Adam มาตรฐานสำหรับ deep learning
- batch 32-256: ช่วงใช้งานจริงคุ้มค่า, ใหญ่กว่านั้นต้องปรับ lr ตาม
- warmup + decay ของ lr: ชะลอตัวช่วงท้ายเพื่อลงจอดอย่างปลอดภัย

## underfit/overfit: อ่านสัญญาณจาก learning curve

Underfit คือโมเดลง่ายเกินหรือยังเรียนรู้ไม่พอ สัญญาณที่อ่านได้คือ ทั้ง train loss และ validation loss สูงพอ ๆ กันและแบนหรือค่อย ๆ ลดลงซื้อไป เมื่อเห็นแบบนี้ แปลว่าโมเดลจับรูปแบบไฟล์ในง่าย ๆ ไม่ได้ ซึ่งสามารถแก้ด้วยโมเดลที่ใหญ่ขึ้น เทรนนานขึ้น หรือเพิ่ม feature ที่ดี
Overfitting คือโมเดลจำได้เฉพาะข้อมูลฝึก (train) แต่ทำพลาดกับข้อมูลใหม่ เหตุผลลึกคือโมเดล "มีกำลังพอ" ที่จะจับ noise เป็นรูปแบบได้ ถ้า parameter เยอะเกินพอดีกับจำนวนข้อมูลจริง สัญญาณที่อ่านจากกราฟคือ gap: train loss ลดต่อ แต่ validation loss ลดลงถึงจุดหนึ่งแล้วกลับสูงขึ้น (หรือยกค้าง) จุดที่ validation น้อยที่สุดคือจุดที่ควรหยุด (early stopping)
ทางแก้อย่าคิดว่า "ทุกทางใช้ได้หมด": ถ้า validate สูงแถม train สูง = underfitting แก้ด้วยโมเดลใหญ่/ข้อมูลดี/เทรนนานขึ้น แต่ถ้า validate สูงและ train ต่ำ = overfitting แก้ด้วย regularization, dropout, เพิ่มข้อมูล (augmentation) หรือลดขนาดโมเดล การเลือกผิดทางจะเสียเวลาเป็นอาทิตย์
กราฟ learning curve วาง train loss กับ validation loss เทียบกับ epoch: เส้น train ต่ำกว่า validation มาก = overfit, เส้นสองอันใกล้กันแต่สูง = underfit, เส้นสองอันใกล้กันและลดต่อเนื่อง = โมเดลกำลังเรียนรู้ดีและอาจต้องเพิ่มข้อมูลหรือเวลาอีก (converging) การอ่านแบบนี้ทำให้ตัดสินใจได้ถูกต้องแทนการเดา
trade-off ที่เห็นชัดคือ หากลดความซับซ้อนเพื่อสู้ overfitting อาจเสีย underfitting คืน การหา sweet spot จึงต้องวัดบน validation ทุกครั้งและทุกการเปลี่ยนสำคัญ ไม่ใช่จากยอดวันที่ train loss ดูสวย และหน่วยความจำของโมเดลที่ overfit อีกด้านก็อาจเป็นประโยชน์ในงานฝึกเฉพาะทาง เช่น งานปรับจังหวะโมเดลจากคำไม่กี่ตัวอย่าง (few-shot fine-tuning)
**ตัวอย่าง — แยกให้ออกก่อนจะแก้**

validation loss = 0.9, train loss = 0.3 → จำมากเกิน (overfit) แก้ด้วย regularization + ข้อมูลและลดความซับซ้อน แต่ถ้า validation = 0.9, train = 0.85 → เรียนไม่พอ (underfit) แก้ด้วยโมเดลใหญ่และเทรนนาน ไม่ใช่ regularization
> [!STOP: อย่าดูแค่ train loss]
> โมเดลที่ train accuracy 99% แต่อาจใช้จริงไม่ได้เลยถ้า validation แย่มาก การดูเฉพาะ train คือวิธีที่สมบูรณ์สุดที่จะถูกหลอกตัวเอง

## bias–variance trade-off: สมดุลที่วัดด้วย validation

ความผิดพลาดของโมเดลแยกได้สองส่วน: bias (โมเดลง่ายเกิน จับรูปแบบไม่ได้ — underfit) กับ variance (โมเดลไวเกิน ตอบเปลี่ยนไปเพียงเพราะชุดข้อมูลเปลี่ยน — overfit) การเพิ่มความซับซ้อนลด bias แต่เพิ่ม variance จุดสมดุลคือจุดที่รวมทั้งสองแล้วน้อยที่สุด ซึ่งหาเจอด้วยการดู validation error ไม่ใช่ train error
อุปมารูปแบบหนึ่งคือ การลากเส้นเล็งตรง (ลด bias แต่ variance น้อย) กับการวัดด้วยจุดหลายจุด (variance สูง) การเล็งตรงบรรลัมโตวาง bias สูงแต่ variance น้อย ส่วนโมเดลซับซ้อนจับรายละเอียดครบทุกอย่างจนvariance พุ่งเพราะเปลี่ยนชุดข้อมูลเพียงเล็กน้อยคำตอบก็เปลี่ยน จุดที่ควรเลือกคือสมดุลที่ validation ต่ำที่สุด ไม่ใช่การเลือกฝั่งใดฝั่งเดียว
ตัวเลข loss รวมเท่ากับ bias กำลังสองบวก variance บวก noise ที่อธิบายไม่ได้ (irreducible) ส่วน noise คือข้อจำกัดของข้อมูลเอง เช่น ป้ายกำกับผิด ไม่ใช่ความผิดของโมเดล การรู้ว่ามี irreducible error ทำให้รู้ว่าโมเดลจะไม่มีวันได้ 0 loss ไม่ว่าจูนอย่างไร เพราะ noise อยู่นอกการควบคุม
ผลเชิงปฏิบัติ: เมื่อเพิ่ม feature หรือขนาดโมเดล ทดสอบเสมอว่าจุดสมดุลอยู่ตรงไหน หลายโมเดล "ดีขึ้นใน train" เพียงเพราะ bias ลดไปจน variance พุ่งทับ — ตัวเลข train ที่ดูสวยจึงไม่ใช่หลักฐาน
trade-off อีกด้านคือ การลด variance ด้วยการเฉลี่ย (เช่น bagging ใน random forest) แต่ยอมสละ bias บ้าง เมื่อโมเดลใหญ่มากอาจเต็มใจยอม bias เพิ่มเล็กน้อยเพื่อดึง variance ลงเยอะ ๆ ซึ่งทำให้ภาพรวมดีกว่าในงานจริง โมเดลง่ายอาจ bias สูงเพราะสมมุติเส้นตรงตรง ๆ ที่ไม่ตรงตามโลกจริง แต่ความมั่นคงต่อการเปลี่ยนข้อมูลดีกว่า โจทย์ดีจึงไม่ใช่ทำให้ bias ต่ำที่สุด แต่หาจุดที่ผลรวมน้อยที่สุด
### สูตร: ความผิดพลาดรวมของโมเดล

E[(y − ŷ)²] = Bias² + Variance + Noise

> Bias คือความผิดอย่างเป็นระบบจากโมเดลง่ายเกิน, Variance คือความไม่เสถียรจากการเปลี่ยนชุดข้อมูล, Noise คือความผิดพลาดที่หลีกเลี่ยงไม่ได้จากข้อมูลเอง
![Underfit is a straight line missing the shape, good fit follows shape, overfit wiggles through noise; total error is U-shaped in complexity](/diagrams/bias-variance.svg)

*Bias–variance tradeoff — ยิ่งโมเดลซับซ้อน bias ลดแต่ variance เพิ่ม จุดรวมที่ต่ำสุด (★) คือจุดที่ validation error ต่ำสุด ไม่ใช่ train error*

## regularization: ลงโทษความซับซ้อนที่ไม่ได้ใช้ให้เท่ากับโมเดลต้องความจริง

L1 (Lasso) ลงโทษด้วยผลรวมค่าสัมบูรณ์ของ weight ทำให้ weight จำนวนมาก "ถูกลดเป็นศูนย์" จริง ๆ — ใช้ตอนอยากให้ feature selection นี่คือคุณสมบัติที่ L2 ไม่มี L2 (Ridge) ลงโทษด้วยกำลังสอง ทำให้ weight เล็กลงแบบกระจาย ไม่เป็นศูนย์ ใช้ลดการฟิตเกินโดยรวม Dropout ซึ่งสุ่มปิด neuron ระหว่างเทรน เป็น Regularization อีกแบบที่บังคับให้โมเดลไม่พึ่ง neuron ตัวเดียว
ความเข้าใจผิดพบบ่อยคือคิดว่า regularization ลด loss ตรง ๆ — ที่จริงมันทำให้ "validation" ดีขึ้นโดยยอมให้ train แย่ลงนิดหน่อย ถ้าเห็น train loss สูงขึ้นพร้อม regularize แปลว่ากลไกกำลังทำงาน ถ้าทั้งคู่แย่ลง แปลว่าแรงเกินไป
Dropout มี trade-off ที่น่าสนใจ: ไม่น่าหยุดใช้เทคนิคอื่น ๆ เพราะทำให้โมเดล robust ต่อการเชื่อมต่อหลายจุด แต่ถ้าตั้งอัตราการปิดสูงเกินไป (เช่น 0.5 ในทุกชั้น) อาจทำให้เทรนช้า ชี้นี้คือแล้ว mise au point ฟังก์ชันต้องปรับตามงานและวัด TELผล
early stopping คือวิธีหยุดเทรนเมื่อ validation เริ่มแย่ลง ป้องกันไม่ให้โมเดลไปทาง overfit แม้ train ยังดีและสวยอยู่ Early stopping เป็นทั้ง regularizer และตัวควบคุมสัมประสิทธิ์ของเวลา พารามิเตอร์: early stopping ยังให้ประโยชน์คือหยุดเวลาที่เหมาะสมแทนที่จะฝืนเทรนให้ครบทุก epoch
weight decay คือ regularization แบบ L2 ที่กำหนดค่าลงโทษน้ำหนักที่ไม่ใช่ศูนย์ และเป็นเครื่องมือมาตรฐานในการเทรน state-of-the-art ทุกวันนี้ การเลือกใช้ Regularization ให้เหมาะคือต้องเลือกที่แรงที่สุด (constraint) ที่ดีที่สุดสำหรับข้อมูลและโมเดลของเรา ไม่ใช่ใส่ทุกเทคนิคพร้อมกันโดยไม่มีหลักฐาน
```python
# L1 vs L2: ความต่างที่เห็นได้จาก weight
import numpy as np

w = np.array([2.0, -1.5, 0.8, -0.3, 0.1])
l1 = np.sum(np.abs(w))       # 4.7 — ดันบางค่าเป็น 0 ได้ (sparsity)
l2 = np.sum(w ** 2)          # 7.39 — แจก weight แบบนุ่ม ๆ ไม่ใช่ศูนย์
print('L1', l1, 'L2', l2)

# Dropout ในฝึก: สุ่มปิด 50% ของ neuron เพื่อไม่ให้พึ่งตัวเดียว
mask = np.random.binomial(1, 0.5, size=100)
print('เหลือเปิด', mask.sum(), 'จาก 100')
```

## debug และทดลอง: วิธีที่ทีมใหญ่ใช้ไม่พึ่งดวง

ลำดับการ debug ที่เชื่อถือได้คือ (1) ดูข้อมูลว่าขนาด, ค่าหาย, ค่าผิดปกติ (outlier) สมเหตุสมผลไหม, (2) ดูว่า loss เริ่มต้นสมเหตุสมผลไหม (เช่น classification เดาสุ่มควรได้ loss เท่ากับ log ของจำนวนคลาส), (3) ดู train loss ว่าเทรนลงไหม, (4) ดู gap ว่าเป็น underfit หรือ overfit, (5) ค่อยปรับ hyperparameter (lr, optimizer, regularization) ทีละอย่าง
การทดลอง ML ต้องบันทึกทุกอย่าง: model version, seed, hyperparameter, และผลลัพธ์ของ validation ทุกครั้ง หากไม่บันทึก จะตัดสินใจจากความทรงจำและพลาดง่าย ตัวเลขใน notebook เปลี่ยนไปโดยไม่รู้ที่มา เมื่อต้องเปรียบเทียบสองโมเดล ต้องยืนยันว่าใช้ข้อมูล split ชุดเดียวกันและประเมินด้วย metric เดียวกันทุกครั้ง
การขาด experiment tracking ไม่ทำให้โมเดลพังตั้งแต่แรก แต่ทำให้ทีมย้อนกลับและยืนยันตอนปรับโมเดลจังหวะท้าย ๆ ไม่ได้ ต้นทุนตรงนี้หลายครั้งสูงกว่าค่าติดตั้งเครื่องมือตั้งแต่ต้น การใช้เครื่องมือแบบ weight & biases, mlflow, neptune หรือแค่ไฟล์ CSV รวมกับ git ก็รักษาความครบไว้ได้พอ
กับดักที่พบบ่อยคือการ เปิดหลาย ๆ แนวคิดแล้วเลือกตัวที่ดีที่สุดโดยไม่ระวังว่า test ชุดนั้นถูกใช้เป็น validation โดยอ้อมไปแล้ว ต้อง lock ข้อมูล test ไว้ตั้งแต่ต้นและประเมินตอนจบทีเดียวตามที่บทวัดผลอีกตอนอธิบายไว้
trade-off ของ experiment tracking คือบันทึกเยอะทำให้ codebase และ deployment หนักขึ้น แต่ข้อดีของ reproducibility มักคุ้มกว่าความสะดวกที่เสียไปในระยะกลาง-ยาว โมเดลที่เทรนได้ซ้ำโดยไม่รู้ว่าต่างกันตรงไหนคือสัญญาณเตือนสำคัญของทีมที่ควรหยุดและแก้ลำดับทำงาน

## ทางเลือกและการอุทธรณ์ปิดบท: เลือกโมเดลตามหลักฐาน ไม่ใช่ตามกระแส

เมื่อเข้าใจวงจรเทรนและการอ่านสัญญาณแล้ว งานของวิศวกร ML ต่อไปคือ เลือกโมเดลที่ตรงกับสมมติฐานของข้อมูลและงานที่ต้องทำ โมเดลใหญ่เหมือนมากเมื่อมีงานแค่ชิ้นเดียวกำลังลงโทษ: ใช้โมเดลใหญ่เกินจะจูนยาก ช้ากว่า ต้องการค่าใช้จ่ายสูง, ความซับซ้อน และบางงานไม่ใช่ทางที่ดีที่สุดเสมอไป หลายงาน linear หรือ tree ยังชนะ deep learning เพราะข้อมูลน้อยและต้องการความอธิบายได้
การเปลี่ยนแปลงโมเดลหรือ hyperparameter ต้องตีความด้วย validation ของชุดเดียวกันทุกครั้งเสมอ และอาจต้องทำ cross-validation สำหรับข้อมูลขนาดเล็กเพื่อความแน่นเพลิดเพลินาน? no โมเดลที่ดูดีขึ้นแค่เพราะโชคดีของ split จะกลับไปเป็นค่าเดิมเมื่อเปลี่ยนชุด ไม่ใช่ความเก่งขึ้นจริง
บทต่อไปเรื่อง Honest Evaluation จะพาเห็นด้านที่การเทรนอย่างเดียวไม่จำเป็น แต่ต้องแจ้งให้ชัด: การแบ่งข้อมูลและ metrics ที่ตรงกับโจทย์ธุรกิจมีความสำคัญมากกว่าซ้ำการเทรนเพื่อ chasing ตัวเลขสวย
