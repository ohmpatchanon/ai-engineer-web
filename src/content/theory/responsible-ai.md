## bias ไม่ได้ "อยู่ในอัลกอริทึม" ล้วน ๆ

อคติ (bias) เกิดได้ 3 จุด: ข้อมูล (ข้อมูลฝึกสะท้อนความเหลื่อมล้ำเดิม เช่น ตัวอย่างผู้หญิงในงานสายเทคนิคน้อย), อัลกอริทึม (optimize บาง metric จนเอียงไปกลุ่มใดกลุ่มหนึ่ง), และการใช้งาน (ผลลัพธ์ถูกใช้กับกลุ่มที่ไม่ได้ตั้งใจ) แต่ละจุดต่อกันเป็นลูกโซ่ การแก้ที่โมเดลอย่างเดียวโดยไม่ดูข้อมูลและการใช้งานจึงแก้ไม่ตรงจุด
อุปมาคือการฝึกทีมให้วิ่งบนเส้นทางลาดเอียงที่ทุกคนไม่มีอุปกรณ์เท่ากัน ต่อให้แผนของคุณดีแค่ไหน คนที่วิ่งบนพื้นที่ไม่เท่ากันก็จะเข้าเส้นชัยไม่พร้อมกันอยู่ดี การดูแค่ตัวเลขรวมของทีมจะไม่เห็นคนที่วิ่งช้าเพราะอุปกรณ์ไม่เท่า จะต้องแยกดูตามกลุ่มเสมอแม้ตัวเลขรวมจะสวย
การวัด fairness ไม่มี "คำตอบเดียวถูก" เพราะแต่ละ metric ให้ความสำคัญกับคนละเรื่อง เช่น group parity ดูว่าผลเท่ากันทุกกลุ่ม แต่บางงานอย่างคัดกรองความเสี่ยง กลุ่มที่ความเสี่ยงต่างกันย่อมได้ผลต่างกันตามความจริง การเลือก metric ที่เหมาะกับโดเมนและอธิบายเหตุผลไว้เป็นการตัดสินใจที่ต้องบันทึก ไม่ใช่ตัวเลขที่แปะไว้บน dashboard
ตรวจสอบ fairness ต้องเริ่มจากการกระจายผลตามกลุ่มตามมาตรฐานทั่วไป ก่อนจะตั้งเป้าว่าต้องเท่ากันตรง ๆ ไม่ตรงตามกฏ เมื่อพบความต่างต้องถามต่อว่าเกิดจากข้อมูล อัลกอริทึม หรือการใช้งาน เพราะคำตอบต่างกันจะเปลี่ยนสิ่งที่ต้องทำต่อไปอย่างชัดเจน
**ตัวอย่าง — ตัวอย่างที่จับต้องได้**

สมมติโมเดลกรอง resume วัดอย่างไรโดยรวมแม่น 92% แต่แม่น 88% ในกลุ่มผู้หญิงและ 96% ในกลุ่มผู้ชาย ซึ่งเป็นตัวอย่างสมมติเพื่อเห็นความเหลื่อมล้ำ ตัวเลขรวมดูเก่งแต่ความต่าง 8 จุดคือสัญญาณว่าต้องถามต่อว่าเกิดจาก resume ตัวอย่างผู้หญิงน้อยหรือวิธีให้คะแนนที่เอียง และต้องแก้ที่ data มากกว่าโมเดล

## privacy: หลักที่ทำให้ "ไม่หล่น" ตามกฎ

หลักการพื้นฐานคือ (1) data minimization เก็บเฉพาะที่จำเป็นต่อภารกิจ (2) consent และ transparency บอกเสมอว่าข้อมูลถูกใช้ทำอะไร (3) anonymization/pseudonymization ลดการย้อนกลับบุคคลได้แต่น้อย (4) access control จำกัดการเห็นตามสิทธิ์และตามความจำเป็นต้องใช้
ความเข้าใจผิดคือการคิดว่าลบชื่อแล้วจบ เพราะหลายฟีเจอร์รวมกันก็ระบุตัวคนได้ (re-identification) เช่น ตำแหน่ง วันเกิดและรหัสไปรษณีย์ ถ้าเก็บเกินจำเป็นและรวมหลายมิติเข้าด้วยกัน ความเสี่ยงจะกลับมาโดยไม่ทันระวัง วิธีที่ถูกต้องคือเก็บน้อยและแยกเก็บพร้อมกำหนดระยะเวลาเก็บ
ระบบที่เรียก LLM กับข้อมูลผู้ใช้ต้องไม่ส่งข้อมูลอ่อนไหวออกไปโดยไม่จำเป็น อาจต้องใช้การรันโมเดลเองก็ได้ ต้องส่งเฉพาะข้อมูลที่ต้องใช้เท่านั้นและต้องปกป้องด้วยสัญญาที่ไม่เก็บข้อมูลหรือวิธีเข้ารหัส ซึ่งต้องปรึกษาทีมกฎหมายก่อนเสมอ
การตรวจก่อนเปิดใช้ควรทำแบบ red team ขั้น "ทดสอบหาข้อมูลรั่ว" เช่น พยายามถามให้ระบบหลุดข้อมูลการฝึกหรือข้อมูลผู้ใช้คนอื่นผ่าน prompt และ tool รวมทั้งการถามซ้ำและหลอกให้ bypass กฎ และห้าม log PII ลงระบบโดยไม่ mask จะต้องเรียงข้อหาในลักษณะที่อธิบายได้ และนำผลที่ได้กลับไปเป็นการทดสอบซ้ำและป้องกันต่อไป

## วัด fairness แบบแยกกลุ่ม พร้อม trade-off ที่ต้องอธิบายได้

การวัดที่คุ้มที่สุดคือแยกผลตามกลุ่ม (sliced eval) ไม่ใช่ดูแค่ตัวเลขรวม เพราะตัวเลขรวมซ่อนความเหลื่อมล้ำของกลุ่มย่อยได้มากมาย ตัวอย่างเช่น อัตราการผ่านกรองของกลุ่มหนึ่งอาจตกลงขณะที่รวมยังดูดี ต้องเห็นภาพแยกกลุ่มทุกครั้งก่อนสรุปว่าโมเดลแฟร์
Fairness มีหลายนิยามที่ขัดกันได้ในงานจริง เช่น demographic parity ต้องการผลเท่า ๆ กันทุกกลุ่ม ส่วน equal opportunity ต้องการอัตราคนที่ผ่านจริงแล้วถูกเลือกต้องเท่ากัน การพยายามให้ทุกนิยามเท่ากันพร้อมกันมักเป็นไปไม่ได้ในทางคณิตศาสตร์เมื่อค่าพื้นฐานต่างกัน จึงต้องเลือกนิยามที่เหมาะกับงานและอธิบายเหตุผลไว้ชัดเจน
Trade-off คือเมื่อเข้มงวดขึ้นด้านหนึ่ง อีกด้านอาจต้องเสีย โดยเฉพาะงานที่ต้องเลือกคนหรือให้คะแนน การเพิ่มความเท่า ๆ กันอาจลดความแม่นที่อิงความเสี่ยงจริงก็ได้ การตัดสินใจต้องเปิดเป็นเอกสารว่าทำไมเลือกนิยามนี้ เวลาใด ใครตัดสิน และจะดูตัวเลขใดเป็นเกณฑ์หยุด
วิธีดูจริงคือตั้งเป้าแบบง่ายที่ป้องกันผลเสีย เช่น ระบุว่าไม่ให้กลุ่มใดต่ำกว่าเกณฑ์ที่กำหนดเมื่อเทียบกับกลุ่มอื่นในเมตริกที่สำคัญ พร้อมกำหนดแนวทางแก้ไขตามสาเหตุว่าเป็นข้อมูล อัลกอริทึม หรือการใช้งาน
### สูตร: ความต่างของอัตราผ่านงานระหว่างสองกลุ่ม

gap = | rate_group_A − rate_group_B |  ;  disparate_ratio = min(rate) ÷ max(rate)

> gap บอกความต่างเชิงสัมบูรณ์ แต่ disparate_ratio บอกสัดส่วนต่ากว่าเท่าไร ควรดูคู่กันและแยกตามกลุ่มย่อย ไม่ใช่ดู gap รวมอย่างเดียว

## red teaming และการวาง human-in-the-loop

Red team คือการตั้งใจโจมตีระบบเพื่อหาจุดล้มเหลว เช่น prompt injection การหลอกข้อมูลภายใน หรือ bypass guardrail ก่อนฝ่ายที่ไม่ประสงค์ดีพบเอง ควรทดสอบทั้ง prompt, tool และข้อมูล โดยรวมถึงเคสที่ข้อความประสงค์ร้ายแทรกมาจากเอกสารซึ่งระบบอาจเผลอดึงใช้โดยคิดว่าเป็นคำสั่งจากผู้ใช้
ผล red team ไม่ใช่แค่พบจุดบัค แต่ต้องถูกนำมาเป็นชุด regression eval ที่รันซ้ำทุกครั้งที่แก้ระบบ เพราะถ้ารันแค่ครั้งแรกแล้วลืม จุดที่เคยแก้จะกลับมาในโลกจริงอีกครั้ง
ระดับ human review ขึ้นกับความเสี่ยง งาน harmless อย่างสรุปอาจตรวจแบบสุ่มตามงบ ส่วนงาน sensitive เช่น การเงิน สุขภาพ หรือการตัดสินใจบุคคล ต้องให้คนอนุมัติก่อน "action" ทุกครั้ง จุดที่ต้องอนุมัติหรือ high-impact tool ต้องมี human approval เสมอ
Human-in-the-loop คือสถาปัตยกรรมไม่ใช่การแค่มีช่องแชทให้คนดู เพราะวงจรการทำงานต้องมีขั้นที่ระบบหยุดและรอคำอนุมัติในเชิงการกระทำ เช่น ห้าม tool ที่ลบข้อมูลหรือส่งข้อมูลออกจากระบบโดยไม่ผ่านการอนุมัติก่อน

## accountability: ขอให้ "อธิบายได้" ไม่ใช่แค่ "แม่น"

ระบบที่รับผิดชอบได้ต้องมีเอกสารการตัดสินใจ เช่น model card (จุดประสงค์, ขอบเขต, ข้อมูล, ข้อจำกัด, ผล fairness) decision log (เหตุผลที่เลือก model/prompt นั้น, ใครตัดสิน, เมื่อไร) version control ของ code, data, prompt, model และ runbook ของความล้มเหลว เพื่อให้ตอบได้ว่าทำไมถึงตอบแบบนั้น
การควบคุมเวอร์ชันสำคัญเท่ากับการควบคุมโมเดลเลยทีเดียว เพราะ prompt หรือการตั้งค่าที่เปลี่ยนไปแค่บรรทัดเดียวก็เปลี่ยนคำตอบได้โดยไม่ต้องเปลี่ยนโมเดล การบันทึก version ทุกส่วนทำให้ย้อนกลับได้และรู้ว่าเปลี่ยนอะไรไปและเมื่อไร
การปล่อยฟีเจอร์ AI ควรเริ่มจากกลุ่มและความเสี่ยงต่ำก่อน แล้วขยายเมื่อตัวชี้วัดผ่าน เช่น ฝึกในหน่วยงานเล็กแล้วค่อยขยายทั้งองค์กร การขยายแบบนี้ทั้งยังลดความเสี่ยงและให้เวลาแก่ทีมปรับคำตอบที่ไม่ตรงอย่างค่อย ๆ เป็นค่อยไป
Guardrail metric และเกณฑ์หยุด (stop condition) ต้องนิยามก่อนเริ่มใช้ เช่น ถ้าความพึงพอใจตกเกินเกณฑ์ที่กำหนดหรือข้อร้องเรียนเพิ่มขึ้นunexpected ต้องหยุดและย้อนกลับ ทุกตัวเลขต้องตอบได้ว่าต้องหยุดเมื่อไร ไม่ใช่เพียงดูไว้เฉย ๆ
> [!ACCOUNTABLE]
> ถ้าอธิบาย "ทำไมเป็นแบบนี้ / ถ้าพังควรทำอย่างไร / ใครรับผิดชอบ" ไม่ได้ แสดงว่ายังไม่พร้อมปล่อย ไม่ว่า accuracy จะกี่เปอร์เซ็นต์

## การเปิดใช้แบบเสี่ยงต่ำ: เริ่มเล็กแล้วขยาย

อย่าเปิดฟีเจอร์ AI ทั่วทุกที่พร้อมกัน ให้เริ่มจากฟีเจอร์ กลุ่ม และความเสี่ยงต่ำ (canary ด้านเสี่ยง) เช่น พื้นที่ที่ไม่มี harm หนัก หรือหน่วยงานเล็ก ๆ แล้วค่อยขยายเมื่อวัดผลผ่านแล้วในด้านความแม่น ความเที่ยงตรง และความคิดเห็นของผู้ใช้
การเลือก canary ด้านเสี่ยงไม่ใช่แค่แบ่งคน แต่ออกแบบตามความเสี่ยงที่จะเกิดกับผู้ใช้มากขึ้น เช่น งานสรุปสามารถเปิดกว้างเร็ว ส่วนงานที่กระทบการตัดสินใจบุคคลต้องเปิดแคบก่อนและตรวจที่เข้มกว่ามาก การแบ่งตามความเสี่ยงจึงสำคัญกว่าการแบ่งตามจำนวนผู้ใช้อย่างเดียว
เมื่อเริ่มเล็กแล้วต้องดูทั้งสองอย่างคือคนใช้เจ็บไหมและระบบทำงานได้ไหม เช่น แม้คำตอบแม่นแต่ผู้ใช้ยังต้องแก้มากก็ไม่ได้หมายความว่าสำเร็จ จึงต้องดูทั้งตัวเลขและงานตรวจสอบจริง เช่น เวลาที่ผู้ใช้ต้องแก้ร่างที่ระบบเสนอ เพราะนั่นคือต้นทุนของความคลาดเคลื่อนของระบบ
Stop condition คือกฎที่เขียนไว้ก่อนเริ่มปล่อย ไม่ใช่หลังเริ่มเห็นปัญหาของระบบ ต้องกำหนดขอบที่ชัดเจนเช่นเกณฑ์คะแนนขั้นต่ำ หรือจำนวนความคิดเห็นเชิงลบที่เพิ่มขึ้นจากเดิม จะต้องหยุดและกลับสู่ระบบเก่าทันที เพราะ stop condition ที่เขียนตามหลังจะไม่ทันเวลาที่ความเสี่ยงเกิดขึ้นแล้ว
