## สิ่งที่ demo ไม่บอก: ความเสถียร

Demo ทำงานกับคน 1 คน เสถียรอย่างเดียวพอ Production ทำงานกับผู้ใช้หลายร้อยพร้อมกัน ท่ามกลาง API ล่มหรือช้า rate limit เครือข่ายผิดพลาด โมเดลที่ "พัง" ไม่ใช่แค่ตรงคำตอบ แต่คือวงจรการเรียกภายนอกทุกจุด งานของวิศวกร production คือเปลี่ยน "ความล้มเหลว" เป็น "การเสื่อมอย่างสง่างาม" (graceful degradation) มากกว่าปล่อยให้ระบบพังทั้งก้อน
อุปมาคือครัวร้านอาหารช่วงพีค เครื่องครัวอาจทำงานได้ดี แต่ถ้าไม่มีระบบรับออเดอร์ ไม่มีคิว และไม่รู้จักส่งจานเก่าก่อน จานใหม่ก็จะม่วนจนออกไม่ทันและพังทั้งร้านทั้งที่ฝีมือดีเหมือนเดิม เรือสำราญลำเดียวกันล่มได้เพราะรูเล็ก ๆ หลายรู ระบบ AI ก็เช่นกัน ไม่ได้พังเพราะโมเดลอย่างเดียว แต่พังเพราะหลายจุดที่ไม่มีใครออกแบบให้เสื่อมไปทีละขั้น
ท่าพื้นฐาน: ตั้ง timeout (สูงสุดที่ยอมรอ) สำหรับทุก downstream call, retry ด้วย exponential backoff + jitter, circuit breaker พอ external พังซ้ำ และ fallback ไปคำตอบที่ถูกออกแบบไว้ (โมเดลเล็ก/template/แคชเก่า) ซึ่งทั้งหมดนี้เป็นโค้ดสถาปัตยกรรม ไม่ใช่ prompt ส่วนเสริม
สัญญาที่ให้ผู้ใช้ (contract) ต้องบอกได้ล่วงหน้าว่าจะตอบช้าแค่ไหน เสียเท่าไร และเมื่อล่มจะเสื่อมไปทางไหน การไม่มีสัญญาแบบนี้ทำให้ demo ที่สวยกลายเป็นภาระตอน load จริงเข้า เพราะทีมไม่มีตัวเลขให้อ้างทั้งภายในและภายนอก
> [!DEGRADE, DON'T CRASH]
> ผู้ใช้ยอมรับ "ตอบช้า" รึ reply ว่า "ระบบไม่ว่าง ลองใหม่" ดีกว่าหน้าจอ error ลายคา — ออกแบบ fallback ทุกจุดวิกฤติก่อนเปิด

## คณิตต้นทุนและ latency ล่วงหน้า

ต้นทุน LLM = (input tokens × ราคา input + output tokens × ราคา output)/1M × จำนวน call โดยแยกให้เห็น input ที่มาจาก context/retrieval (ส่วนที่ขยายไวตามขนาดเอกสาร) ถ้า RAG ขนาดเอกสารใหญ่ input จะครองต้นทุน เพราะทุกคำถามต้องถือเอกสารหลายชิ้นไปด้วย การลด input ด้วยการตัดและ rerank จึงลดต้นทุนได้เร็วกว่าการสลับโมเดล
อุปมา: โรงหนังคิดค่าตั๋วต่อใบ แต่ถ้าทุกคนเอาของมาวางเบาะข้าง ๆ จนเต็มแถว โรงหนังก็ต้องขยายพื้นที่จ่ายค่าเช่าเพิ่ม เอกสารที่ดึงมาแต่ละครั้งก็เหมือนการวางของหลายชิ้นใน context ถ้าใส่เกินความจำเป็น เจ้าของระบบจะจ่ายค่าเช่า (token) ทุกครั้งบ่อยและซ้ำเหมือนเดิม
Latency ของ LLM ส่วนใหญ่คือ time-to-first-token (TTFT คือเวลารอตัวอักษรแรก) บวกความช้าต่อ token (output) กับ batching/queue ในช่วง load สูง ถ้าจะรับประกัน p95 ต้องทดสอบโหลดจริงแบบ concurrent ไม่ใช่ทดสอบทีละคำถาม แต่ต้องเข้าใจก่อนว่า p95 คือค่าที่ 95% ของคำขอเร็วกว่าและมีแค่ 5% ที่ช้ากว่านั้น ซึ่งผู้ใช้จะเจอบ่อยกว่าค่าเฉลี่ยเสมอ
ตัวอย่างจำนวนแบบง่าย สมมติ queue 0.3 วินาที retrieval 0.2 วินาที TTFT 0.8 วินาที และ output 300 tokens ด้วยความเร็ว 50 tokens ต่อวินาที จะใช้เวลาส่วน decode ประมาณ 6 วินาที ทำให้เวลารวมราว 7.3 วินาที แม้โมเดลจะเขียนไวตามปกตา การลดความยาว output หรือใช้ streaming ทำให้ผู้ใช้เห็นตัวอักษรเร็วขึ้น และลดความรู้สึกว่ารอนานโดยไม่ได้แก้โมเดลเลย
Trade-off พื้นฐานคือ throughput กับ latency ไปตรงข้ามกัน เมื่อรวมหลาย request เป็น batch เดียว ระบบจะรองรับได้มากขึ้นและประหยัดต่อหน่วย แต่ผู้ใช้แต่ละคนต้องรอนานขึ้นเพราะต้องรอแถวครบกลุ่ม เหมือนครัวที่รอครบโต๊ะก่อนเสิร์ฟ ควรเลือกให้ชัดว่าจะรองรับเยอะหรือเสิร์ฟเร็ว แล้วระบุไว้เป็นสัญญา ไม่ใช่หวังได้ทั้งสองอย่างพร้อมกัน
### สูตร: ต้นทุนต่อเดือน

cost = ((in_tok×p_in + out_tok×p_out)/1e6) × requests

> อย่าลืม embeddings, retrieval, prompt ระบบที่บังคับ (system) และ retry ที่ทำซ้ำ input เดิมทุกครั้ง รวมถึง output ยาวที่มักประเมินต่ำนี่เองที่ทำให้ต้นทุนจริงสูงกว่าที่คิด

## strategies: cache, แบตช์ และ stream

Cache ชั้นดี: (1) cache ด้วย key ที่ปรับ normalize (คำถามที่พบบ่อย/embedding ที่ deterministic), (2) prompt/context cache (provider เก็บ prefix เหมือน ถามต่อเนื่อง ราคา input ลด), (3) cache การค้น (same doc version) วัด hit rate ก่อนลงทุน เพราะ cache ที่ไม่เคยโดน = เสียเงินเปล่า
Batch (รวมงานหลายคำขอเป็น inference ครั้งเดียว) ช่วย throughput และประหยัด แต่เพิ่ม latency รายคำขอ เหมาะงานออฟไลน์/คิว ไม่ใช่ real-time UX Streaming เปลี่ยนการรับรู้ latency: แม้ TTFT เท่าเดิม ผู้ใช้รู้สึก "เร็ว" เมื่อเห็นอักษรไหล เกือบทุกแชท UI ควรเป็น streaming
วิธีวัดว่าแคชคุ้มหรือไม่คือ hit rate และต้นทุนที่ประหยัดได้จริง ไม่ใช่แค่มีโค้ดแคชอยู่ เพราะแคชที่ key ไม่ตรงกันหรือข้อมูลเก่าจะไม่เคยโดนและทำให้คำตอบล้าสมัย ถ้าต้องแคชคำตอบจริงให้เก็บ model, prompt version และ timestamp ไว้เพื่อเช็คว่าคำตอบเก่ายังใช่ในเวอร์ชันใหม่หรือไม่
การสลับใช้กลยุทธ์ให้เหมาะกับงานคือ แชทสดใช้ streaming และแคชสั้น ส่วนงานเอกสารและงานเบื้องหลังใช้ batch และคิว เพราะได้ UX ที่ดีกับงานที่สำคัญและต้นทุนที่ต่ำกับงานที่รอได้ ซึ่งดีกว่าการใช้กลยุทธ์เดียวกับทุกงานโดยไม่แยกแยะ
- cache คำถามซ้ำ: ต้อง normalize คำถามและเก็บ version ไว้ ไม่ใช่ match string ดิบ
- prompt/prefix cache: ใช้กับงานต่อเนื่องหรือ system prompt ยาวที่ซ้ำบ่อย
- batch: เหมาะงานออฟไลน์และงานไฟล์ อย่าใช้กับ UX สดที่ต้องรอการตอบชัดเจน
- streaming: ใช้กับแชทเกือบทุก UI เพราะการรับรู้ latency ดีกว่า synchronous มาก

## เลือกโมเดลให้พอดีงาน ไม่ใช่ใหญ่สุดเสมอ

ไล่จากเล็กสุดที่ eval ผ่าน เพราะบ่อยครั้งโมเดล 3-8B ทำงานธรรมดาได้ในราคาและความเร็วที่ดีกว่า 10 เท่าเมื่อเทียบกับโมเดลใหญ่ เช่น สรุป ประเภทงาน แปลภาษาและการเขียนสั้น ๆ ใหญ่กว่าจึงไม่ได้คุ้มกว่าเสมอไป ต้องพิสูจน์ด้วย eval ก่อนสรุป
แยกเส้นทางด้วย router แบบง่าย ใช้โมเดลเล็กเป็นด่านหน้าสำหรับงานสั้นและซ้ำ แล้วยิงงานที่ยากหรือต้องใช้เครื่องมือไปยังโมเดลใหญ่ตามเกณฑ์ที่กำหนดไว้ เช่น ความยาวคำถามหรือคำสำคัญพิเศษ วิธีนี้ได้ทั้งความเร็วและต้นทุนที่สมดุลโดยไม่ทิ้งคุณภาพงานยาก
ก่อนสลับโมเดลควรมี eval ที่วัดทั้งความถูกต้อง การทำตามรูปแบบ และความสอดคล้อง ไม่ใช่แค่ว่าตอบไวและถูกเงิน ส่วน quantization (การบีบ precision ให้เล็กลง) ช่วยลดการใช้หน่วยความจำและเพิ่มความเร็ว แต่ต้องวัดว่า precision loss ทำให้คุณภาพหล่นหรือไม่เมื่อเทียบกับค่าตั้งต้น
การเลือก self-host แทนการยิง API เป็น trade-off ระหว่างการควบคุมข้อมูลและความเสถียร กับต้นทุนการดูแลเครื่องและ GPU เอง ส่วน API ใช้งานได้เร็วกว่ามากแต่ต้องรับ rate limit และรับความเปลี่ยนแปลงจากเจ้าของระบบภายนอก การตัดสินใจควรมาจากต้นทุนต่อ task จากตัวเลขจริง ไม่ใช่ระดับเทคโนโลยีที่ใหญ่กว่ากัน
> [!ROUTER]
> เส้นทาง: งานสั้นและซ้ำ ใช้โมเดลเล็กและแคช คำถามยากหรือต้องเรียงข้อมูล ใช้โมเดลใหญ่ตามเกณฑ์ที่ระบุไว้ แล้ววัด engineering hit rate ของ router ทุกสัปดาห์ ไม่ใช่เดาว่าใหญ่กว่าคุ้มกว่า

## resilience คือโค้ด ไม่ใช่คำปรารถนา

Timeout คือเส้นตายที่บอกว่า "รอได้สูงสุดเท่าไร" สำหรับทุก downstream ทั้ง LLM, retrieval และ tool ต้องมีครบทุกขั้น เพราะการไม่มี timeout ทำให้ request ค้างเป็นพันตัวจนกินหน่วยความจำและลากระบบช้าลงทั้งก้อน ไม่ใช่แค่ตัวที่ล่ม
Retry ใช้เมื่อล้มเหลวชั่วคราว เช่น 429 หรือ 503 แต่ retry มั่วจะทำให้เกิด storm เพราะทุกฝั่งพยายามพร้อมกันยิ่งกด external ให้ล่มหนักขึ้น ต้องใช้ exponential backoff คือรอ 1 วินาทีแล้ว 2 วินาทีแล้ว 4 วินาที พร้อม jitter คือสุ่มเวลารอเพิ่มเล็กน้อยเพื่อไม่ให้ทุกงานตื่นพร้อมกัน และกำหนด retry ไม่เกิน 2 ถึง 3 ครั้ง
Circuit breaker คือสวิตช์ตัดไฟเมื่อ external ล้มเหลวซ้ำเกินเกณฑ์ที่กำหนดไว้หลายครั้ง ระบบจะหยุดยิงไปหาจุดที่ล้มเหลวและให้คำตอบตามเส้นทางสำรองแทนการรอเก้อหรือเดาออกไป ระบบจึงไม่ถูกดึงตามไปด้วยทั้งระบบเมื่อจุดใดจุดหนึ่งพัง
การแยกส่วน (isolate) คือการแยก quota ต่อคนและแยกงานชิ้นออกจากกันเพื่อให้ชิ้นหนึ่งพังแล้วงานอื่นยังหายใจได้ ส่วน fallback ต้องเป็นการตอบที่ถูกออกแบบไว้ เช่น โมเดลเล็ก แคชเก่า หรือข้อความบอกสถานะที่สุภาพ ไม่ใช่การเดาคำตอบที่ไม่มีหลักฐาน
```python
import time, random

def call_with_backoff(client, req, max_retry=3):
    delay = 1.0
    for attempt in range(max_retry + 1):
        try:
            return client.generate(req, timeout=15)
        except Exception:
            if attempt == max_retry:
                return fallback_answer(req)
            wait = delay * (1 + random.random() * 0.3)
            time.sleep(wait)
            delay *= 2
```

## capacity, quota และสัญญา: การเตรียมพร้อมก่อนเปิดประตู

Capacity planning คือการประมาณว่าต้องรองรับคำขอไหนพร้อมกันและจำนวนเท่าไรในโหลดจริง ปัญหาคือการประมาณจากค่าเฉลี่ยไม่พอ เพราะผู้ใช้จริงมาเป็นระลอกและแต่ละคำถามใช้ token ไม่เท่ากัน ดังนั้นต้องทดสอบโหลดแบบ concurrent ด้วย prompt และ context จริงหลายระดับ เพื่อเห็นจุดคอขวดและค่า p95 ก่อนเปิดใช้
Rate limit คือเส้นคุ้มกันทั้งกับ provider ภายนอกและกับผู้ใช้เอง เช่น จำกัดรายคนที่ 30 request ต่อนาที เพื่อกันโควตาหมดจากผู้ใช้รายเดียวและกันคิวลากทั้งระบบ ต้องแยก quota รายคนและราย workspace เพื่อให้คนหนึ่งงานหนักแล้วคนอื่นยังใช้งานได้
การเตรียมแผนต้องมี budget alert ต้นทุนรายวัน แยกต้นทุนจาก embedding, generation และบริการภายนอก ตั้งคิวแบบมี backpressure ให้งานรอและค่อย ๆ ป้อนเข้ามาเมื่อระบบฟื้นตัวแทนการอัดโหลดจนล้ม พร้อมเก็บ log ต้นทุนต่อคำขอเพื่อย้อนกลับได้เมื่อมีคำถามว่าทำไมแพง
สุดท้ายต้องมีสัญญาที่พูดกันรู้เรื่อง เช่น ช้ากว่าเท่าไรถือว่าช้า fallback ใช้ได้ถึงขั้นไหนและผู้ใช้รู้สถานะของระบบผ่านช่องทางใด อย่าแจ้งสัญญาที่สวยเกินจริง เพราะสัญญาที่ทำไม่ได้จะเหนื่อยกว่าการแจ้งตามจริงที่ทำได้
