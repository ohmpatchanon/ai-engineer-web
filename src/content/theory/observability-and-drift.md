## วัดไม่ได้คือเดา: สามเสาหลักของ observability

เจตนาของ observability ไม่ใช่การมี dashboard สวย แต่คือทำให้ทีมตอบคำถามย้อนหลังได้ว่าคำถามนี้ไปทางไหน เจอเอกสารอะไร ถูกยิงให้โมเดลไหน ใช้เวลาและต้นทุนเท่าไร ถ้าตอบไม่ได้ทีละคำถาม จะต้องเดาสาเหตุเมื่อคุณภาพตกและแก้แบบสุ่ม ซึ่งทำให้ทุกอย่างช้าลงไปหมด
สามเสาหลักคือ logs บอกว่า "เกิดอะไร" metrics บอกว่า "เกิดนานและถี่แค่ไหน" และ traces บอกว่า "แต่ละขั้นเชื่อมต่อกันอย่างไร" งานทั่วไปมักขาด trace จึงเห็นตัวเลขแต่ไล่ต่อไม่ได้ งานที่คุ้มที่สุดคือเก็บ trace ต่อคำขอให้ครบก่อนจะเพิ่ม dashboard อื่น ๆ
อุปมาคือห้องนักบินไม่ได้ดูแค่เข็มทิศอย่างเดียว แต่ดูความสูง ความเร็ว และเครื่องยนต์ทุกตัวเพราะเครื่องบินเสื่อมที่อื่นได้โดยไม่เตือนล่วงหน้า ระบบ AI ก็เช่นกัน ตัวเลขเฉลี่ยดีไม่บอกว่าคนใช้รู้สึกแย่ และต้องมีตัวชี้วัดนำที่เห็นสัญญาณเตือนก่อนตัวเลขสุดท้ายจะพัง
กฎง่าย ๆ คือถ้าต้องเลือกเก็บให้น้อยที่สุด ให้เก็บ trace id, model, prompt version, latency, token, cost และผลสุดท้ายทุกคำขอ เพราะจากสิ่งเหล่านี้คำถามส่วนใหญ่ย้อนดูได้ก่อนที่จะมีข้อมูลครบทั้งหมด
> [!TRACE FIRST]
> เริ่มจาก trace ที่เห็นทุกขั้นตอน จากนั้นค่อยสรุปเป็น metrics ไม่ใช่เริ่มจาก metrics สวย ๆ แล้วภายหลังรีบสร้าง tracing ขึ้นมา เพราะ eval อย่างเดียวไม่ได้ชี้ว่าพังตรงไหน

## สิ่งที่คนลืม log แล้วเดือดร้อนภายหลัง

ระบบ AI ต้อง log ให้ต่อเนื่องเป็นสายเดียวกัน: trace id ที่ผูกกับทุกขั้นตั้งแต่ query เอกสารที่ดึงกลับมา prompt ที่สร้าง model และ version ของการตั้งค่าจนถึง output, latency และ token เพื่อให้เห็นเส้นทางทั้งหมด หากไม่มี trace id แต่ละคำขอจะแยกกันเป็นชิ้นและไม่มีทางดีบักได้เมื่อระบบมีหลายส่วน
จุดที่ลืมบ่อยที่สุดคือ config และ prompt version เพราะเมื่อทีมแก้ prompt ไปหลายรอบแล้วไม่มีตัวบ่งชี้ว่าการตอบแบบนั้นมาจากการตั้งค่าใด การเทียบผลก่อนและหลังจะไม่ได้แน่นอน อย่าลืมเก็บ version ทุกครั้งแม้จะดูเล็กน้อย เช่น template prompt, retrieval parameter, rerank model และ max output
กฎความเป็นส่วนตัว: ห้าม log ข้อมูลอ่อนไหว (เนื้อหาผู้ใช้) เปล่า ๆ ให้ใช้ hash/redact หรือ log เฉพาะ metadata และตัวอย่างสุ่มที่ mask แล้ว พร้อมกำหนด retention ที่ชัดเจน การ "log ทุกอย่าง" โดยไม่ mask คือหนี้ทางกฎหมายและต้องแก้ภายหลังแพงกว่ามาก
การเก็บทุกคำขออาจมากเกินไป ให้ใช้การเก็บแบบเน้นจุดสำคัญ เช่น เก็บคำถามที่ผิดพลาด 100% และงานทั่วไป 5% ถึง 10% พร้อมแยกตามประเภทคำถามและตามความสำคัญ เพื่อให้ทีมตรวจบทผิดพลาดได้โดยไม่ต้องเก็บทุกอย่างไปจนเกินความจำเป็น
```json
{
  "trace_id": "tr_abc123",
  "model": "model-x",
  "prompt_version": "v2026-11",
  "retrieved": ["doc_123", "doc_045"],
  "latency_ms": 1800,
  "input_tokens": 3200,
  "output_tokens": 412,
  "cost_usd": 0.042
}
```

## online metrics: วัดสิ่งที่ eval ออฟไลน์มองไม่เห็น

Offline eval บอกว่า "โมเดลนี้ตอบถูกไหมในชุดที่ควบคุมตัวแปรแล้ว" แต่ไม่เห็นของจริงว่าผู้ใช้จริงถามอะไร ใช้ต่อหรือไม่ โมเดลถูกเรียกด้วย context ใหญ่แค่ไหน ต้นทุนจริงเท่าไร และ p95 latency เป็นอย่างไร จึงต้องมี online metrics คู่กันแทนที่จะหวังให้ eval อย่างเดียวตอบแทนของจริงได้
Online metric ควรเชื่อมกับสิ่งที่วัดได้ตรง เช่น acceptance ของร่างที่ผู้ใช้กดส่ง การยกเลิกกลางคัน การแก้ไขหลังร่าง การคลิกแหล่งข้อมูล อัตราที่งานถูกส่งกลับมาแก้ และอัตราที่ผู้ใช้กดไม่พอใจ เพราะสิ่งเหล่านี้คือสัญญาณที่ผู้ใช้ให้โดยตรงและไม่ต้องตีความแทนจาก eval
การเทียบก่อนและหลังต้องทำแบบมีเวลาเสมอ เพราะพฤติกรรมของตลาด เอกสารและสถานการณ์เปลี่ยนไปตามเวลาแม้โมเดลยังไม่ได้เปลี่ยน การเทียบสัปดาห์ชนสัปดาห์โดย fixed version จะทำให้เห็นการกระทบของการตั้งค่าที่เปลี่ยนไปอย่างเป็นธรรม ไม่ใช่ความบังเอิญของฤดูกาล
อีกเครื่องมือที่คุ้มคือ golden set ที่อัปเดตจาก trace ตัวจริง โดยการเก็บคำถามและคำตอบที่ตรวจแล้วเป็นชุดอ้างอิงเพื่อทบทวนทุกครั้งที่ prompt หรือ model เปลี่ยน ซึ่งทำให้ eval ไม่แข็งอยู่ที่ชุดเดิมและสะท้อนของจริงมากขึ้นเรื่อย ๆ

## drift คือต้นตอของ "เมื่อวานยังดี วันนี้พัง"

โมเดลไม่ได้ "พัง" จากโค้ดที่เปลี่ยนอย่างเดียว แต่พังจากสิ่งที่รอบตัวเปลี่ยนได้บ่อยกว่า เช่น input distribution เปลี่ยนเมื่อผู้ใช้เริ่มถามแบบใหม่จากสถานการณ์ใหม่ data source เปลี่ยนเมื่อเอกสารใหม่หรือ format ใหม่เข้ามา หรือ behaviour ของผู้ใช้เปลี่ยนเมื่อผู้ใช้เริ่มคลิกหรือปฏิเสธในลักษณะใหม่
ในระบบ RAG drift พังง่ายเพราะเอกสารเปลี่ยนทำให้ทุกครั้งที่ดึงผลจะต่างไปทันที การเฝ้าต้องไม่ใช่แค่ว่า accuracy ลดแค่ไหน แต่ต้องดูอัตรา refusal, citation rate, อัตราที่ไม่ได้รับคำตอบจากเอกสาร และความหลากหลายของคำถาม เพื่อเห็นสัญญาณก่อนที่คุณภาพจะหล่นจริง
เมื่อเชื่อว่าเกิด drift ให้ดู trace จริงเป็นระลอกสุ่มและเรียงตามกลุ่มหรือตามเวลา เช่น กลุ่มคำถามใหม่หรือเอกสารแบบใหม่ที่เริ่มมากแค่ไหน พร้อมแนวโน้มรายสัปดาห์และตามเวอร์ชัน เพราะ drift มักเป็นคลื่นที่สะสมขึ้นมาและไม่เห็นในทันทีบน dashboard
การตอบสนองต้องมีแผนที่รู้ล่วงหน้า (runbook) แทนการแก้แบบตกใจ เช่น จะอัปเดตเอกสาร จะปรับ threshold หรือจะปรับ prompt ใหม่และต้องประเมิน eval อีกครั้ง การแก้แบบลืมบันทึก version ทุกครั้งจะทำให้ drift คลื่อนไปเรื่อย ๆ และกลับมาเตือนซ้ำอีกที
### สูตร: ตัวเลขเช็คว่าการกระจายเปลี่ยนไปเท่าไร (PSI เบื้องต้น)

PSI = Σ (actual_pct − expected_pct) × ln(actual_pct ÷ expected_pct)

> ค่า PSI ประมาณ 0.1 คือเปลี่ยนเล็กน้อย 0.1 ถึง 0.25 คือเปลี่ยนพอควรและ 0.25 ขึ้นไปถือว่าเปลี่ยนมาก ใช้เช็คการกระจายของ input และ output แบบคร่าว ๆ ไม่ใช่ตัดสินด้วยตัวเลขอย่างเดียว
> [!LEADING vs LAGGING]
> สร้างสัญญาณเตือนล่วงหน้า (early warning) ที่เห็นก่อนคนบ่น เช่น เวลาและต้นทุนขึ้น อัตรา tool error ขึ้น citation rate ลง พอ threshold ข้ามให้แจ้งทีมหรือเปิด runbook อัตโนมัติ

## canary, shadow และ rollback: ปล่อยของใหม่แบบระมัดระวัง

การปล่อยโมเดลหรือ prompt ใหม่พร้อมกันทั้งระบบเหมือนซื้อรถใหม่แล้วขับทางไกลทันทีโดยไม่ลองก่อน วิธีที่ปลอดภัยกว่าคือปล่อยทีละ 5% ก่อน ดูตัวชี้วัดและค่อยขึ้นเป็น 25% ที่ไฟเขียว ทำแบบนี้ทำให้กล้าปล่อยของใหม่และถ้าของใหม่มีปัญหาจะกระทบผู้ใช้น้อยคนที่ออนไลน์อยู่เท่านั้น
Shadow คือการรันของใหม่คู่ขนานกับของที่ผู้ใช้อยู่เพื่อเปรียบเทียบคำตอบและต้นทุนโดยไม่กระทบผู้ใช้จริง แต่ข้อเสียคือต้องจ่ายต้นทุนคู่และข้อมูลที่ได้ไม่เท่ากับสิ่งที่ผู้ใช้จริงเจอ ดังนั้นให้ใช้เป็นขั้นตอนก่อน canary ไม่ใช่แทน canary ได้
Rollback ต้องทำได้ด้วยปุ่มเดียวและการย้อนการตั้งค่าต้องทำได้ทันที ไม่ใช่เริ่มกระบวนการ deploy ใหม่ทุกครั้ง version ของ prompt, model และตัวเลือกต้องสลับได้ทันที เพราะเวลาที่หยุดหน่วงคือเวลาที่ผู้ใช้รอระบบคิดใหม่
การเปรียบเทียบใน canary ต้องใช้เกณฑ์เดียวกันทั้งกลุ่มควบคุมและกลุ่มทดสอบ เช่น acceptance rate, edit distance และ task success พร้อมแยกตัวชี้วัดตามกลุ่มงานและช่องทางเพื่อให้แน่ใจว่าของใหม่ไม่ได้ดีเฉพาะในกลุ่มง่าย ๆ

## alertที่ไม่น่ารำคาญ: leading มาก่อน lagging

Alert ที่ดีไม่ใช่เตือนทุกครั้งที่ตัวเลขสุดท้ายตก แต่ต้องมี early warning เห็นก่อนคนบ่น เช่น เวลา TTFT หรือต้นทุนต่อคำขอค่อย ๆ ขึ้น citation rate ค่อย ๆ ลดหรือ tool error rate เริ่มขึ้น พร้อมกำหนด threshold ที่รู้ล่วงหน้าว่าเมื่อไรต้องเริ่มทำอะไร
ทีมต้องกำหนด threshold แบบง่าย เช่น p95 latency เกิน 8 วินาทีติดกัน 5 นาที tool error เกิน 5% หรือ citation rate ลดเกิน 10% เพื่อเริ่มกระบวนการตรวจ วิธีนี้ทำให้ทีมตรวจเชิงรุกและไม่รอจนคำถามจากคนใช้เข้ามาหลายใบ
การแยกสัญญาณเป็นระดับช่วยให้ทีมตอบเร็วและไม่ตื่นเต้นเกินเหตุ เช่น ระดับเตือนแต่ไม่ล้ม ระดับกระทบผู้ใช้หลายกลุ่ม และระดับหยุดระบบ พร้อมเชื่อมถึง runbook ที่ตรงกับเหตุ ทั้งนี้ข้อความตอบที่ผู้ใช้เห็นต้องสุภาพและสอดคล้องไม่ว่าอะไรจะพัง
Dashboard ที่สำคัญคือภาพรวมต่อหนึ่งระบบ เช่น task success, feedback rate, ต้นทุนเฉลี่ยหนึ่งคำขอ, p95 latency, error rate และตัวเช็ค drift ของ input พร้อมการเทียบรายสัปดาห์ ไม่ใช่ dashboard รวมทุกอย่างที่ไม่มีจุดให้ตอบ

## วงจรเรียนรู้: จาก trace สู่ eval ใหม่

การดูย้อนหลังที่ดีต้องดู trace ราว 20 ถึง 50 รายการที่สุ่มจากตัวจริงเพื่อแยกสาเหตุที่เป็นระบบ ไม่ใช่เปิดดูผู้ใช้หนึ่งหรือสองคน เพราะหลายปัญหาอาจเป็นรายเคสที่หายไปเมื่อเก็บตามระบบแล้ว หรือเป็นลักษณะคลัสเตอร์ที่ซ้ำกันแต่ไม่ปรากฏบน dashboard
ชุด trace ที่พบว่าเป็นปัญหาอย่างเป็นระบบควรถูกแปลงเป็นชุด eval ใหม่โดยการเขียนคำตอบที่ถูกและผิดเป็น test case เพื่อให้ครั้งต่อไปวัดเรื่องเดียวกันได้ทันที นี่คือวิธีเปลี่ยนประสบการณ์จริงให้เป็นการป้องกันในอนาคต
เมื่ออัปเดต eval ใหม่ให้ใส่ทั้งเคสหลักและเคสเปราะ เช่น คำถามแบบใหม่ เอกสารแบบใหม่ หรือพารามิเตอร์ที่ยังไม่ได้ finalize เพื่อให้ eval ตัวหน้ามีความเที่ยงตรงมากขึ้นแทนการจับความรู้สึกเท่านั้น แม้ตัวเลขเฉลี่ยจะไม่ตก ทีมก็พร้อมรับการเปลี่ยนครั้งต่อไป
สรุปคือ observability ไม่ใช่แค่กราฟ แต่คือนิสัยของทีมที่เห็นว่าของจริงเปลี่ยนไปทางไหนและต้องทำอะไรต่อให้ทันเวลา นิสัยนี้ทำให้ drift แบบค่อย ๆ เปลี่ยนกลายเป็นเรื่องที่เห็นได้ก่อนที่จะทำให้คุณภาพเสีย
