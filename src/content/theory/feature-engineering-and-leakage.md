## Feature คือ "มุมมอง" ไม่ใช่คอลัมน์ดิบ

Feature คือข้อมูลที่ตั้งใจ "ตีความ" จากข้อมูลดิบเพื่อให้โมเดลเห็นความสัมพันธ์ที่ยังมองไม่เห็น ตัวอย่าง: วันที่ให้เป็น day-of-week, month, days_since_last_purchase, ไม่ใช่ timestamp ดิบ คอลัมน์ข้อความให้เป็น word count, จำนวนเครื่องหมาย, has_url คุณสมบัติของ feature ที่ดีคือ มีความหมายเชิงเหตุผลกับปัญหาและกระจายตัวไม่ถูกรุ่งหนึ่งค่าจนโมเดลใช้ไม่ได้
ความผิดพลาดยอดนิยมคือ dumping ทุกคอลัมน์ดิบเข้าโมเดลแล้วปล่อยให้มัน "หาความหมายเอง" — โมเดล tree ทำได้บ้าง แต่โดยรวม data น้อย/ขยะเยอะจะทำให้ overfit ควรเริ่มด้วย feature น้อยที่กลั่นจากเหตุผล แล้วค่อยเพิ่มโดยวัดว่า validation ดีขึ้นจริงหรือไม่ (forward selection เชิง evidence) มากกว่าการอัดทุกอย่างที่คิดออก
feature engineering มาตรฐานแบ่งได้เป็น numeric (การเปลี่ยน scale, log, square, root), categorical (one-hot, frequency, target), และ time/text (เช่น วันที่ให้เป็น season) แต่ละเฟรมต้องมีเหตุผลชัดเจนและต้องวัดผลเสมอ หลักการคือ ให้ feature ใหม่เกิดจากข้อสันนิษฐานที่เกี่ยวกับโจทย์ ไม่ใช่สุ่มทดลองแบบไม่มีทิศทาง
trade-off ของ feature เยอะคือ สัญญาณชัดขึ้นแต่เสี่ยง overfit และต้องดูแลมากขึ้น ดังนั้นควรทำสองทิศทางเสมอ: เพิ่ม feature ตามเหตุผลแล้ววัด validation ว่าเพิ่มขึ้นตอนทดสอบแต่ละครั้ง การ feature ไม่มีลอกออกก็ดีที่สุดเพราะแสดงความกล้าหาญเสียเปรียบในการมีพิษที่เท่าเทียมแต่มีสัญญาณน้อยกว่าการแยกกันกลาง
มุมมองที่สำคัญคือ feature ไม่ใช่แค่การแปลข้อมูล แต่เป็นการสื่อสารกับโมเดลว่า "ส่วนไหนของข้อมูลควรสำคัญ" ข้อมูลดิบพูดภาษาเดียวกับโมเดลได้บางส่วน แต่ feature ที่ดีจะชี้ทางให้โมเดลหาว่าส่วนไหนมีประโยชน์โดยไม่ต้องเดินหาทั้งตาราง โจทย์ที่แก้ด้วย feature ดี ๆ มักจะรีดประสิทธิภาพโดยไม่ต้องเปลี่ยนโมเดลเลย
```python
import pandas as pd

df = pd.DataFrame({'date': pd.to_datetime(['2024-01-01', '2024-01-03', '2024-01-15']), 'amount': [100, 250, 80]})

# แปลงข้อมูลดิบเป็น feature ที่มีหมาย

df['day_of_week'] = df['date'].dt.dayofweek      # 0-6 แบ่งพฤติกรรมวันต่อวัน
df['month'] = df['date'].dt.month
df['amount'] = df['amount'].astype(int)
print(df)
```

## scaling, imputation และ outlier: เตรียมตัวเลขให้เท่ากัน

scale ของตัวเลขที่กว้างต่างกันจะทำให้โมเดลที่อิงระยะทาง/gradient (linear, SVM, neural) ร่างผิดทางเพราะ feature ใหญ่กว่า (เช่น อายุ) จะมีอิทธิพลกว่า feature เล็ก (เช่น คะแนน) แม้ทั้งสองมีความสำคัญเท่า ๆ กัน การทำ standard scaling (ลบ mean หาร std) หรือ min-max scaling จะปรับให้อยู่ในสเกลเดียวกัน แต่อาจมีข้อเสียกับข้อมูลที่มี outlier
Imputation คือการจัดการข้อมูลหาย: ใช้ mean/median ของคอลัมน์, ใช้โมเดลทำนายค่า, หรือใช้ KNN จับค่าใกล้เคียง วิธีที่เลือกต้องดูความเป็นไปได้ของข้อมูลและผลต่อโมเดล การใส่ค่า 0 หรือค่ากลางโดยไม่รู้เนื้อแท้ทำให้โมเดลไปทางผิดได้ เหตุผลเสมอสำหรับงานต่าง ๆ ต้องถูกกำหนด แต่ละ decision ต้องไม่เอาข้อมูลอนาคตทั้งชุดไว้ไปยุ่งลงใน value นั้น
outlier คือจุดผิดปกติ (เช่น รายได้ 1,000,000 ในข้อมูลที่ปกติอยู่หลักพัน) ซึ่งอาจบิดการคำนวณของ mean/std และการปรับ scale ทั้งชุด การแก้สามารถทำโดยตัดค่าอนาคุก (clipping), log transform, หรือใช้ค่าที่ Robust ต่อ outlier มากกว่า การ decisions outlier ต้องเสริมด้วยเหตุผล ไม่ใช่การรู้ว่าผิดปกติแล้วพามันออกโดยไม่ดูว่า outlier นั้นคืออะไรในสมการ
ข้อบังคับสำคัญคือ ทุกการแปลงที่อ่านค่าสถิติจากข้อมูลต้อง fit เฉพาะ train แล้ว apply ลง val/test ต่อไปนี้คือวิธีหลักที่ป้องกัน leakage แม้การจัดการข้อมูลที่ดูเบาเช่น imputation แต่ก็เป็นต้นรั่วที่อาจเปลี่ยนสถิติทั้งชุดได้โดยไม่รู้ตัว
tree-based model ไม่ต้อง scale เท่า linear/neural เพราะแตก split จากการจัดลำดับของค่าต่าง ๆ ไม่ได้ใช้ตัวเลขเชิงบวก/ลบ การเตรียมที่ scale เกินอาจไม่เสียแต่ต้องไม่กระทบต่อค่าเชิงเวลาในการไล่ซ้ำ ๆ ปัญหานี้ต้องชั่งน้ำหนักระหว่าง neural ที่ข้อบังคับ scale ทุกประการ และการฝากไว้เรื่อง inference เขา dense จนกลบข้อมูลใส่ตัวเลขปกติของ scale อนิมิต
trade-off ของ outlier manipulation นั้นมีทั้งสองด้าน: outlier จัดการกับ clipping หรือ threshold แต่ก็ยังแบ่งเป็นโจทย์ของงาน งานที่ outlier คือตัวชี้วัดสำคัญ (เช่น fraud detection) การลบหรือตัด outlier อาจกำจัดเงาะเคสที่โมเดลจำเป็น ทุกการตัดสินใจจัดการ outlier ต้องวัดผลก่อนตัดสินทุกครั้งเสมอ

## encoding ชนิดข้อมูล categorical หมวดหมู่

categorical encoding คือการเปลี่ยนข้อความหรือหมวดหมู่เป็นตัวเลข ไม่ใช่เจ้าอารมณ์ แต่ต้องตัดสินใจอย่างรอบคอบ: label encoding ดีเพียงเมื่อหมวดมีลำดับธรรมชาติ (เล็ก/กลาง/ใหญ่) เพราะตัวเลขนั้นสามารถแสดงลำดับในสายตาโมเดล แต่ถ้าไม่มีลำดับเช่น สี หรือชื่อเมือง การใช้ label encoding จะทำให้โมเดลไปทางผิดเพราะเห็นว่า "กรุงเทพ=3 สูงกว่าเชียงใหม่=1" ทั้งที่ไม่มีเหตุใดบอก
one-hotencoding (การแปลงทุกหมวดเป็นคอลัมน์ศูนย์/หนึ่งแยกกัน) แก้ปัญหาลำดับเทียมได้ดี แต่กลายเป็นคอลัมน์มากมายเกินไปเมื่อหมวดมีหลากหลาย (เช่น ที่อยู่, ชื่อสินค้า 10,000 รายการ) ซึ่งอาจก่อให้โมเดลหนักเกินไปโดยไม่จำเป็น target encoding สนในทางตรงข้ามยิ่งกว่าโดยเอาค่าเฉลี่ยของ target มาวิเคราะห์เป็นตัวแทน แต่ยังต้องทำ cross-validated เพื่อแก้ leakage แม้ encode แบบนี้จะแรงกว่ากับค่ารั่วที่น่ากลัวกว่าการ scale ธรรมดา
frequency encoding คือการใส่หมายถึงความบ่อยของหมวดที่มี (word count) เป็นตัวแทน ใช้สะดวกแต่ยังพยากรณ์มุมมองที่โมเดลไม่เจอทางหนึ่งเท่านั้น key หลักของโจทย์นั้นถูกเปลี่ยนทุกครั้งที่รบบางเข้ารหัส: ถ้าชุด train มีหมวดที่ไม่ปรากฏใน test เป็นเรื่องจะต้องถูก จัดทดวายและทำ fallbacks ให้ถูกต้องเสมอ
การเตรียมข้อมูล categorical ต้องมีการทำ one-hot/target encode บน(train) และ apply บน validation/test ด้วยคำสั่ง fit_transform/transform ทำให้สามารถ reuse โดยไม่รู้กันข้อมูลอนาคตได้ รากของการรั่วบ่อยสุดครั้งนี้มักเกิดเดียวไม่ย่อยง่ายเพราะ encode ผิดจังหวะก่อน split
trade-off ของ encoding คือความละเอียดกับความระดับผันผวน: target encoding ให้ความแม่นและความชัดเจนดีมาก แต่ผันผวนมาโดยทีมทดสอบ ถ้าไม่ทำ cross-validation อย่างเข้มงวดผลใน lab สวยแต่เมื่อทำ inference จริงค่าจะพัง One-hot และ frequency encode เสถียรแต่ไม่เจาะจง ข้อมูลจำเพาะน้อยที่สุด อนุมานบนตัวเลขชุดแรกอาจ ไม่ก็ยังต้องระวังที่เขียนมาแล้วบอกว่าทดลองค่าหลายครั้ง จริงๆแล้วใน testing เราเช็คไม่ครบโดยไม่รู้ตัว
ตามด้านระบุประสิทธิภาพทั้งหมดที่กล่าวแล้ว ภายใต้ระเบียบ ข้อควรค้นหาจากผู้ปฏิบัติจริงคือ ใช้เครื่องมือ pipeline ทำการ fit สองรอบสลับกันใน train เท่านั้น และใช้คำสั่ง transform เหลี่ยมเมตาตัวอื่นกับ validation/test ที่ทดสอบชุดอื่น วิธีนี้ทำให้การ encode ปลอดภัยและสอดคล้องได้ไม่เป็นปัญหาในงานที่ต้อง generalizeโดยไม่กลัวว่าเลื่อนเลื่อนเรื่องข้อมูล
เมื่อเข้าใจเรื่อง encoding คู่ๆ นี้แล้ว dégradation ของโมเดลจากข้อมูล categories เกี่ยวข้องกับ hyperparameter แบบเต็มและสถาปัตยกรรม (cross-cross-dimension) ที่สามารถสืบสวนข้อมูลระดับนี้ และโมเดลขนาดแรกอื่น ๆ จะมีค่าข้อมูลที่เหมาะกับงานแต่ละ نوع
```python
from sklearn.preprocessing import OneHotEncoder
import pandas as pd

# Label encoding ใช้ไม่ได้กับหมวดที่ไม่ลำดับ (สี/เมือง/ไอดี'
# One-hot ดีกว่า: แปลงแต่ละหมวดเป็นคอลัมน์ศูนย์/หนึ่ง
enc = OneHotEncoder(sparse_output=False, handle_unknown='ignore')

train = pd.DataFrame({'city': ['กรุงเทพ', 'เชียงใหม่', 'กรุงเทพ', 'ภูเก็ต']})
val = pd.DataFrame({'city': ['กรุงเทพ', 'พัทยา']})  # พัทยาไม่เคยเห็นตอนฝึก

enc.fit(train[['city']])          # fit เฉพาะ train เท่านั้น
print(enc.transform(train[['city']]))   # shape (4, 3) — พัทยาไม่ชน
print(enc.transform(val[['city']]))     # พัทยา -> [0,0,0] (handle_unknown)
```

## feature ของเวลาและข้อความ: มุมมองที่ทำให้งานง่ายขึ้น

วันที่มักให้ทั้งวันของสัปดาห์, เดือน, ไตรมาส, วันหยุด, และระยะเวลาตั้งแต่เหตุการณ์ล่าสุดมา (days_since_last) ซึ่งเก็บพฤติกรรมได้ดีกว่าการใช้ timestamp ตรง ๆ เพราะโมเดลเห็น season ผ่าน day_of_week ได้ลดเงียบมาก
ข้อความมักแปลงเป็นสถิติความยาว, จำนวนคำ, ความหนานุ่ม, ความรุนแรง, และความมีปฏิญาณ หรือใช้ word embedding สีลงมา เป็น feature ที่โมเดล tree ออกจากข้อมูลแรกได้เลย ข้อเสียคือข้อมูลเหล่านั้นจำกัดมาก แต่ต้องใช้ Tfidf/n-gram หรือร่วมกับความหมายของคำเป็น embedding ให้ครบมิติระดับการมองลึกไม่ใช่แค่ word count อย่างเดียว
บทที่สองนี้เน้น trade-off ตรงที่ feature พื้นฐานไม่สวยงามเหมือน list ของข้อมูลจากภายนอกเหมือนตอนไปขอกู้ยืมสถิติของแต่ละย ใกหนึ่งชางทำก่อน ด้วยโมเดล NLP ต้องประทับเครื่องความหมายระดับข้อความเหมือนดิบตัวเลขทั่วไป และหลายโมเดล อ้างความเป็นคำสั่งเป็นชุดและเป็นdifference อีกแบบหนึ่ง ข้อเสียคือความซับซ้อนแต่มีให้รางวัลของ feature ที่แม่นยำมากกว่า
ความเสี่ยงของการใช้ข้อมูลของเวลา/ข้อความโดยไม่ทำแปลงละเอียดคือ โมเดลจะไปทางผิดเพราะ transaction วันที่สุมข้อมูลซ้อนเลื่อนชุดอย่างระมัดระวังและใช้ทุก feature ที่มีข้อมูล
Feature เวลาและข้อความที่มีจากข้อมูลดิบยังต้องเฝ้าระวัง vertical leakage ที่ต้องใช้ทุกอย่างกรณีดึงมาจากระบบเข้าซื้อยิ่งกว่าเดิมหากเป็น feature โปรแกรมของโมเดลกับข้อมูลภายในอาจพรุ่งนี้ระวังเสมอด้านต้นคำตอบแล้วจะใช้ความพิศวงเฮๆ แบบขอแค่เข้าเป้า
> [!STOP: ลองแปลงก่อนอัปเกรดโมเดล]
> ถ้าโมเดลยังไม่แม่น ลองแปลงวันที่เป็นวันของสัปดาห์/เดือนและข้อความเป็น word count/has_url ก่อน — feature ดี ๆ มักชนะโมเดลแพง ๆ ที่จูนไม่ดี

## leakage 5 รูปแบบที่พบบ่อยในโปรเจกต์จริง

- Split หลัง imputation/encoding: สถิติเต็มชุดรั่วเข้า feature (fit ก่อน split ค่าที่ได้รั่วมาจาก test)
- Feature อนาคตรีบ: เช่น "ยอดสั่งซื้อเดือน" ในข้อมูลพยากรณ์วันที่ผ่านมา หรือข้อมูลที่ยังไม่เกิดเมื่อทำนาย
- Duplicate/near-duplicate แถวข้ามชุด: ข้อมูล 96% เหมือนใน train กับ test สูงเกินจริง (ข้อมูลเหมือนกันคนละแถว)
- Target-derived: สร้าง feature จากคอลัมน์เป้าหมายหรือ proxy ของมัน (เช่น การใช้รายได้ในอนาคตไปทำนาย)
- โมเดลเห็นกลุ่มทดสอบระหว่างเทรน: เช่น ข้อมูลคนเดียวไม่แยกเป็น user group (ต้องใช้ group split)

## ทดสอบและแก้ leakage: วิธีที่จับได้จริง

วิธีจับง่ายที่สุด: split ตามเวลา (หรือกลุ่ม) อย่างเคร่งครัด แล้วเช็คว่า validation ลดลงมากจาก split แบบสุ่มหรือไม่ — ถ้าลดฮวบ แสดงว่า split สุ่มกำลัง "ให้โชค" ด้วยการรั่ว เลือกวิธีแบ่งข้อมูลจะต้องมาจากลักษณะของงานและต้องดูขนาดความต่างของ metric เปรียบเทียบคู่ขนานกับแบบ split สุ่มเพื่อเห็นผลกระทบชัดเจน
ดู metadata ที่แปลก เช่น accuracy สูงเกิน 99% ในงานยาก ๆ บ่งชี้ว่า test ใกล้ train เกินไป ให้สุ่ม check ซ้ำว่าซ้ำกับ train จริงหรือไม่ และให้ examiner ตรวจสอบ attribution ของ feature ที่สำคัญว่ามี provenance ผิดปกติไหม ถ้าชุด feature ที่บังคับตอบถูกแทบสมบูรณ์ก็ต้องสงสัย target-derivation ทันที
เครื่องมือช่วยคือการรันโปรเจกต์ใหม่ด้วย "unseen 100%" (ข้อมูลใหม่หลัง cutoff) แล้วเทียบ: ถ้าตัวเลขจริงต่ำกว่า lab มาก อย่าโทษ "โลกจริง" ก่อน — ให้กลับมาหา leakage ใน pipeline ก่อนเสมอ
เทคนิคตรวจเพิ่มเติมคือ error analysis เฉพาะจุด: เลือก false positive แบบโหดออกมาแล้วดูว่าจริง ๆ มี feature ที่ซ่อน target ไว้หรือเปล่า บางครั้งการทำนายนั้นย้อนกลับไปเปลี่ยนคำตอบได้โดยตรง เช่น ใช้ค่าติดตั้งโปรแกรมไปเป็นบันทึกการซื้อ
trade-off ของการแก้ leakage คือ เสียข้อมูลบางส่วนและต้องปรับ pipeline ให้ strict ตั้งแต่ต้น ต้องใส่ pipeline fit/transform แบบถูกต้อง จึงได้ตัวเลขที่ถูกต้องกับโลกจริง แทนที่จะหลงกับตัวเลข lab ที่สวยแต่เท็จทุกครั้ง

## ตรวจสอบว่าโมเดลใช้ feature อะไรและทิ้งตัวไหน

การตรวจสอบ feature คือส่วนสำคัญของการ debug โมเดล: permutation importance สุ่มสับค่าของ feature พร้อมกันและดูว่า metric ตกแค่ไหน SHAP อธิบายผลของ input ที่แต่ละ feature ได้ดีกว่าการใช้ impurity importance โมเดลอธิบายแค่บางส่วนให้เข้าใจว่าทำไมโมเดลเลือกตัวตอบที่อธิบายไม่ได้ก่อน เทคนิคเหล่านี้ทำให้การตัดสินใจเกี่ยวกับ feature เป็นหลักฐานแทนการเดา
Interaction feature คือค่าที่สร้างจากตัวเลขคูณกันของสอง feature มักช่วยให้โมเดลเห็นอะไรบางอย่างที่มันไม่เห็นจาก feature เดี่ยว ๆ เช่น feature ยอดซื้อของลูกค้ากับขนาดออเดอร์สามารถสะท้อนสไตล์การซื้อได้แม่นกว่าแต่ละขนาดเดียว น่าเสียดายที่แต่เมื่อสร้าง feature ที่แม่นแล้ว โค้ดแปลงยังต้องfit ใน train เท่านั้นไม่ให้ leak
L1 regularization ยังเป็นตัวเลือกที่ผลัก weight ที่ไม่สำคัญให้เป็น 0 ทำให้โมเดลเลือก feature อัตโนมัติในโมเดล linear, ส่วน boosting (เช่น XGBoost) หลังเทรนจะแสดง feature importance ที่ชี้ว่า feature ไหนจำเป็น และงานเมื่อต้องอธิบายควรเลือก técnicas ตรวจสอบซ้ำ แล้วตัดทิ้ง feature ที่ใช้ไม่ได้ต่อไป
การตัด feature ไม่คุ้มค่ามักไม่เพิ่ม accuracy แต่ลด workload ของโมเดลและลด noise ดังนั้นต้องวัดเพื่อแก้ให้ลด ไม่ใช่ปล่อยให้รกเพิ่มขึ้น
trade-off ที่ต้องเข้าใจคือ โมเดลที่ตัด feature ตามเหตุผลบางครั้งจริงออก อาจได้ความแม่นน้อยลงแต่สอนงานที่แปลกไหม เมื่อต้อง deploy production จำเป็นต้องมี feature list ที่ชัด และโมเดลที่ดีกว่าเพิ่มเองและตัดเองโชว์ประสิทธิภาพที่แม่นยำกว่าแบบ exhaustive search มาก
แนวทางที่ควรทำก่อน deploy คือ ablation test: ตัดเป็นจังหวะและวัด metric เทียบว่า feature ที่ทิ้งไปเปลี่ยน performance แค่ไหน ถ้า metrics ไม่เปลี่ยนก็ตัดทิ้งไป ใช้เหตุผลออบ และเลือกทำแอปจากชุดข้อมูลและโมเดลที่ตรวจสอบแล้วว่าดึงทุกอย่างในชุดทดสอบเป็น factor นี้

## pipeline ที่ถูกต้องและการส่งต่องานจริง

pipeline ที่ถูกต้องคือ การรวม preprocessing (imputation, scaling, encoding) และโมเดลในกล่องเดียวเพื่อให้ fit เฉพาะ train แล้วทำ transform บนชุดอื่น ซึ่งช่วยกัน leakage ได้แนบแน่น ทดสอบต้นแบบด้วย sklearn Pipeline แล้วรันสคริปต์ทดสอบผ่านการ train/validation/test ชุดจริงเสมอ อย่าทำให้ถือฟังก์ชัน fit/transform ไปใช้ก่อนที่โมเดลเตรียม fit ใน training จับ
ข้อควรกำหนดระดับความปลอดภัย history: ทุกครั้งที่จะ deploy ต้องยืนยันว่าโมเดลนั้น trained ผ่าน pipeline ที่ถูกต้อง ไม่ใช่ training script ที่ไม่มี provenance ถูกฝึก และต้อง validate ใหม่ด้วย ข้อมูล unseen 100% ที่เป็นสรุปตามกฎที่กำหนดของทีม ทะลุโดยไม่ตรวจและต้องตรวจให้ดีก่อนการ deploy เสมอ
นอกจากนั้นต้องคำนึงถึงการทำ inference ใน production: feature pipeline ทดสอบ ทดสอบเสมอว่า input จากแอปมีรูปร่างและประเภทถูกต้องตามโมเดล หากทำ fail หลายจุด จำเป็นต้องรับ error กลางข้อใครจะสลับ input ใส่โมเดลให้ดีที่สุด
trade-off หนึ่งที่ต้องสื่อสารให้ทีมคือ feature ที่สร้างขึ้นจะเพิ่ม burden ใน production (compute/ดูแล) แต่ก็ดีกว่าการซื้อโมเดลแพง ๆ ที่ไม่ stable ทุกครั้ง การส่งงานในดาวน์ไลน์จึงต้องเลือกจากงานทดลองและข้อจำกัดของ production พร้อมกัน ไม่ใช่ค่าที่ labor แบบสุ่ม
บทต่อไปจะขยายประเด็นเรื่องการจัดการโมเดลที่ไปกับข้อมูลจากภายนอกที่ใช้ ไม่ใช่คุณภาพ feature เดี่ยว ๆ แต่ความมั่นคงของวิธีทำงานและคุณภาพของการคำนวณแบบสมบูรณ์
```python
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression

# Pipeline ที่ทำทุกอย่างได้ครบโดยไม่รั่ว
pre = ColumnTransformer([
    ('num', Pipeline([('imp', SimpleImputer(strategy='median')), ('sc', StandardScaler())]), ['age', 'income']),
    ('cat', OneHotEncoder(handle_unknown='ignore'), ['city']),
])
pipe = Pipeline([('pre', pre), ('clf', LogisticRegression(max_iter=1000))])
pipe.fit(X_train, y_train)          # fit เฉพาะ train เท่านั้น
print('val', pipe.score(X_val, y_val))
print('test', pipe.score(X_test, y_test))  # ใช้ตอนเดียวสุดท้าย
```
> [!GOLDEN RULE]
> ทุกอย่างที่คำนวณจากข้อมูล (mean, min, encoding, imputation) ให้ fit เฉพาะ train และนำไป reuse กับ val/test — ห้ามอัปเดตสถิติจากชุดที่ "เป็นอนาคต"
