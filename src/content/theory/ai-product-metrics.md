## model metric ไม่ใช่ business metric

โมเดล "แม่น 95%" อาจไม่เปลี่ยนยอดขายเลยถ้า metric ผิดจากที่ธุรกิจต้องการ ขั้นตอนคือตั้ง north star (ผลที่ผู้ใช้หรือธุรกิจเห็นจริง เช่น "ลูกค้าตอบเสร็จเร็วขึ้น X นาที") แล้วแปลงลงเป็น model metric เช่น correctness หรือ completeness ของ draft เพื่อให้ model metric เป็นตัวแทน (proxy) ของคุณค่าทางธุรกิจ
ตัวอย่าง: ผู้ช่วยสรุปอีเมล มี model metric เป็น BLEU/faithfulness ส่วน business metric คือเวลาที่ผู้ใช้เปิดอีเมลต่อวันและจำนวนอีเมลที่ตอบจบ ส่วน north star คือ "ชั่วโมงที่ประหยัดได้ต่อคนต่อสัปดาห์" ถ้าโมเดลเก่งแต่คนใช้น้อยก็หมายความว่า model metric ดีแต่ product metric แย่ ห้ามสับสน
อุปมาคือแช่แข็งเนื้อตุ๋นที่สวยแต่ไม่มีคนซื้อ เพราะรสชาติไม่ใช่สิ่งที่ตลาดต้องจ่ายเงิน ทุก model metric ต้องตอบได้ว่าแล้วผู้ใช้หรือธุรกิจได้อะไร ถ้าตอบไม่ได้ให้เปลี่ยน metric ใหม่ก่อนจะลงทุนต่อ
การเชื่อม model metric กับ business metric ควรมี funnel ระหว่างกลาง เช่น ผู้ใช้เห็นร่างกี่ครั้ง กดใช้กี่ครั้ง และงานจบในเวลานานเท่าไร เพื่อให้รู้ว่าโมเดลดีแต่คนไม่กดเพราะปัญหา UX ไม่ใช่เพราะโมเดลไม่เก่ง
> [!CONNECT IT]
> ทุก model metric ควรตอบได้ว่า "แล้วธุรกิจหรือผู้ใช้ได้อะไร" ถ้าตอบไม่ได้ เปลี่ยน metric ใหม่ก่อนจะลงทุนต่อ

## ตั้ง metrics แบบ leading/lagging และ guardrail

ติดทั้ง leading (ก่อนผลสุดท้าย: engagement ระหว่างใช้, latency, ต้นทุนต่อ request, error rate, citation rate) และ lagging (ผลท้าย: retention, task completion, การประหยัดเวลาและเงิน) โดย leading เป็นสัญญาณเตือนล่วงหน้าก่อน lagging จะเปลี่ยน และกำหนด guardrail metric เช่น ความพึงพอใจหรือการลาออกต้องไม่ตก เพื่อไม่ให้ optimize ตัวเดียวแล้วทำลายอีกด้าน
AI-specific ที่ต้องเพิ่มคือต้นทุนต่อ session (token และการเรียก) time-to-value (วินาทีแรกที่ได้ประโยชน์) และ escalation/human-review rate เพราะฟีเจอร์ AI ดูเหมือนฟรีทาง UX แต่อัดต้นทุนและความรับผิดชอบที่ต้องเฝ้าอยู่เป็นประจำทุกวัน และถ้าไม่เฝ้าค่าต้นทุนจะเพิ่มขึ้นโดยไม่มีใครรู้
อุปมาคือสิ่งที่ดูเหมือนคันเร่งแต่ไม่ใส่เกียร์ เข็มความเร็วยืนได้แต่รถไม่เคลื่อนเพราะเกียร์คือคุณค่าที่ผู้ใช้เห็น ทุกฟีเจอร์ AI ควรมีเกียร์คือผู้ใช้ต้องเห็นผลประโยชน์จริง ไม่ใช่แค่ตัวเลขที่สวย
Trade-off คือการเพิ่มตัวชี้วัดมากไปก็ไม่ดี จะทำให้เหนื่อยเกินไปและยากที่จะรู้ว่าตัวไหนคือเข็มสำคัญจริง ดังนั้นควรเลือกเฉพาะ leading ที่เห็นก่อน lagging จริง ไม่ใช่ใส่เข้าไปเยอะเพียงเพราะดูเท่

## experiment กับ AI: เล็กกว่าที่คิดแต่อยากกว่าที่ดู

AI output ไม่ deterministic เพราะมี temperature และระบบมักเปลี่ยนบ่อย จากโมเดลหรือ prompt ดังนั้นต้องตั้ง seed หรือ fixed sampling ให้กลุ่ม experiment เทียบกันได้ และ fix version ทั้งระบบสำหรับทั้ง experiment เป็นอย่างน้อย
ผู้ใช้เรียนรู้จาก AI ไปเรื่อย ๆ ไม่ได้หยุดเพียงแค่ครั้งแรกที่เห็นข้อความ ดังนั้นอย่าวัดแค่วันแรกเพียงอย่างเดียว ควรวัดระยะ 2 ถึง 4 สัปดาห์เพื่อให้เห็นการเปลี่ยนแปลงของพฤติกรรมและการใช้ซ้ำกันมากขึ้น
งานบางอย่างมี snowball/network effect ที่ผลลามไปหลายกลุ่ม ดังนั้นต้องดู guardrail และสุ่มทั้งระบบ ไม่ใช่ตรวจเฉพาะคนใกล้ชิด ผลที่เกิดขึ้นอาจสะสมจากการใช้งานหลายระดับและการกระจายผลจะไม่กระจายไปถึงทุกคนของระบบทันที
กลุ่มตัวอย่างเล็กและข้อมูลไม่ปกติ ดังนั้นควรเลือก metrics ที่ robust เช่น median/p95 และใช้ design ของ experiment ที่เข้มงวด ไม่ควรตัดสินใจเร็วเพียงเพราะตัวเลขเปลี่ยนในช่วงที่เก็บตัวอย่างน้อย
- AI output ไม่ deterministic (temperature) ให้ตั้ง seed หรือ fixed sampling เพื่อให้กลุ่ม experiment เทียบได้
- context และระบบเปลี่ยนบ่อย (model update, prompt เปลี่ยน) ให้ fix version สำหรับทั้ง experiment
- ผู้ใช้เรียนรู้จาก AI และใช้ไปเรื่อย ๆ แบบต่อเนื่อง อย่าวัดแค่วันแรกเพียงอย่างเดียว ให้ดูผลช่วง 2 ถึง 4 สัปดาห์
- snowball/network effect บางงานผลกระจายไปหลายกลุ่ม ให้ดู guardrail ควบคู่และสุ่มทั้งระบบ
- กลุ่มตัวอย่างเล็กและข้อมูลไม่ปกติ ให้เลือก metric ที่ robust (median/p95) และใช้ experiment ที่เข้มงวด

## นำเสนอให้ stakeholders ฟังแบบ ROI และ unit economics

แทนที่จะโชว์ว่า "accuracy ขึ้น 2%" ให้เล่าเป็น "ช่วยเวลาคน 5 นาทีต่อวันโดยเฉลี่ย ถ้าทีม 100 คนใช้ทุกวัน ภายในหนึ่งเดือนจะประหยัดได้กี่ชั่วโมง และถ้าตีเป็นจำนวนชั่วโมงเปรียบเทียบกับตำแหน่งงานนั้นเท่าไร" พร้อมต้นทุนรวมทั้ง token, GPU, annotation เพื่อให้ trade-off เห็นชัด
ถ้าจะเพิ่ม accuracy อีก 3 จุดต้องใช้ annotation อีก 300 ชั่วโมงถึงจะคุ้ม ต้องถามก่อนว่าคุ้มหรือไม่ โดยการเปรียบเทียบเป็นจำนวนเงินและจำนวนชั่วโมงที่จะประหยัดได้ต่อเดือนในทิศเดียวกัน ให้การตัดสินใจเป็นเรื่องของธุรกิจไม่ใช่เรื่องของเทคโนโลยีอย่างเดียว
อุปมาคือการเปิดร้านอาหารที่คุณทำอาหารอร่อยแต่ไม่รู้ต้นทุนของวัตถุดิบแต่ละจาน คุณจะกำหนดราคาอาหารไม่ได้และไม่รู้ผลประโยชน์ที่ร้านจะได้ ดังนั้นต้องมี unit economics ของฟีเจอร์ AI ทั้งต้นทุนต่อ task, เวลาที่ได้คืนมา และต้นทุนงานดูแลต่อเนื่อง
การนำเสนอที่ดีต้องมีทางเลือก 3 แบบชัดเจนคือ ราคาถูกแต่คุณภาพลดลงเป็นระยะ กลาง ราคากลางแต่ได้คุณภาพสูง และแพงแต่ได้คุณภาพสูงสุด พร้อมระยะเวลา to-market ที่แตกต่างกัน เพื่อให้ผู้ตัดสินใจเห็นภาพการแลกกันได้และเปรียบเทียบได้ทันที
### สูตร: unit economics แบบง่าย

value_per_task = hours_saved × hourly_value  ;  cost_per_task = token + infra + review

> ทุนต่อ task ต้องรวม token, infra และเวลาคนตรวจ ถ้าขาดสิ่งเหล่านี้จะประเมิน ROI ต่ำไปทุกครั้ง

## จาก discovery ถึงการดูแลฟีเจอร์อย่างต่อเนื่อง

ฟีเจอร์ AI ต้องการการค้นพบ (discovery) ซ้ำ ๆ เพราะประโยชน์จะเปลี่ยนตามเวลาและบริบทขององค์กร เมื่อเวลาผ่านไปหลายเดือน ประโยชน์ของระบบจึงอาจลดลงแบบค่อย ๆ หรือลดลงแบบซ่อน ๆ โดยไม่มีใครรู้สึกในทันที
อุปมาคือการเรียนเปียโน คนจะเล่นไวขึ้นเมื่อฝึกเรื่อย ๆ เพราะนิ้วจับจังหวะได้แม่นขึ้น และจะช้าลงอีกเมื่อหยุดฝึกไปนาน ฟีเจอร์ AI ก็เช่นกัน ถ้าไม่พัฒนาต่อจะค่อย ๆ ล้าสมัยและผู้ใช้จะใช้ประโยชน์น้อยลงเรื่อย ๆ
เพื่อป้องกันภาวะที่ฟีเจอร์ถูกลืม ต้องมีวงจรการทบทวนจาก trace และ feedback เป็นประจำ ซึ่งของจริงจากผู้ใช้มักแม่นกว่าแผนวิเคราะห์บนกระดาษเสมอ
เมื่อถึงเวลาที่ฟีเจอร์โรยต้องตัดสินใจโดยดูเวลาทำงานและต้นทุนต่อ task ที่เหลือ ว่าควรทิ้งไปหรือปรับให้คุ้มค่ากว่าการไปทำฟีเจอร์อื่นแทน การปล่อยฟีเจอร์ที่ไม่มีใครใช้ค้างไว้โดยไม่แก้จะดึงทรัพยากรออกไปโดยเปล่าประโยชน์

## วงรอบเรียนรู้จากตัวเลขไปสู่การตัดสินใจ

ความสำเร็จของโปรดักต์ AI ไม่ได้วัดได้แค่ครั้งเดียวตอนเปิดใช้ แต่ต้องมีวงจรเรียนรู้จากตัวเลขอย่างสม่ำเสมอ เช่น ดูเวลาใช้งาน ต้นทุนต่อ task และการตอบสนองของผู้ใช้ทุกสัปดาห์ เพื่อให้มองเห็นว่าส่วนไหนกำลังจะพังและรู้ไวพอที่จะแก้
เมทริกที่สำคัญที่สุดคือ time-to-first-value เพราะเป็นวินาทีแรกที่ผู้ใช้รู้สึกว่าฟีเจอร์นี้คุ้มค่า ถ้าต้องรอนานเกินไปผู้ใช้อาจเลิกใช้และไม่กลับมาอีก ควรดูตัวเลขนี้คู่กับขั้นตอนแรกของผู้ใช้และแก้ให้เร็วพอ
การติดตาม time-to-first-value, acceptance rate และ edit rate ต้องดูคู่กัน เพราะตัวชี้วัดตัวเดียวอาจดูดีแต่ไม่บอกว่าผู้ใช้ได้ประโยชน์จริง ต้องดูทั้งสามพร้อมกันเพื่อรู้ว่าคุณภาพที่ได้ถูกต้องจริงหรือไม่
คำถามสุดท้ายที่ทีมต้องถามเสมอคือ ถ้าต้องใช้เวลาและทรัพยากรเพิ่มเติมไปแล้วจะคุ้มหรือไม่ ทีมจึงควรมีข้อมูลที่เชื่อถือได้จากการสังเกตต่อเนื่องเพื่อให้ตัดสินใจได้ว่าเมื่อไรควรหยุดและเมื่อไรควรต่อ
