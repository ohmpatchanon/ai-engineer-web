## จาก RNN สู่ข้อจำกัดของลำดับ

โมเดลภาษาแบบก่อนหน้าเชื่อว่า RNN และ LSTM อ่านทีละ token แล้วอัปเดต state ซ้ำไปเรื่อย ๆ เพื่อจำบริบทไว้ใช้ในภายหลัง แต่วิธีนี้ต้องคำนวณทีละขั้นอย่างต่อเนื่อง จึงช้าเมื่อประมวลข้อความยาวและยากที่จะจำข้อมูลที่ไกลออกไปได้อย่างครบถ้วน ซึ่งอธิบายว่าทำไมงานภาษายาว ๆ ถึงเป็นจุดอ่อนของสถาปัตยกรรมเหล่านั้น
Transformer เปลี่ยนแนวคิดจากการอ่านแบบลำดับเป็นการมองภาพรวมของข้อความทั้งหมดโดยตรง ทำให้ token ทุก token มองเห็น token ทุกตัวได้ในครั้งเดียว นั่นคือหนึ่ง hop ที่ผู้ออกแบบดั้งเดิมให้เหตุผลว่าการเข้าใจบริบทที่ยาวต้องเริ่มจากการไม่ต้องไล่ทีละ token
การมองภาพรวมทำให้เทรนขนานกันได้ และเทรนเร็วขึ้นอย่างมีนัยยะเมื่อประมวลข้อความหลายร้อย token แต่ก็มาพร้อมต้นทุนการคำนวณที่เพิ่มขึ้นตามกำลังสองของความยาว ผู้ใช้จึงต้องออกแบบสมดุลระหว่างความยาวบริบทและต้นทุนในทุกการใช้งาน
### สูตร: Scaled dot-product attention

Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V

> QKᵀ ให้คะแนน "ความเกี่ยวข้อง" ของทุกคู่ หารด้วย √dₖ เพื่อกันคะแนนถล่ม → softmax ให้เป็นน้ำหนัก → ถ่วง V รวม

## queries, keys, values: การเปรียบเทียบแบบพจนานุกรม

คิดง่าย ๆ ว่า keys คือป้ายของแต่ละ token ที่บอกว่า token นั้นสนใจอะไรเป็นพิเศษ ส่วน queries คือสิ่งที่ token ปัจจุบันกำลังมองหา และ values คือเนื้อหาจริงของแต่ละ token ระบบคำนวณว่า query ตรงกับ key ของ token ใดมากเป็นพิเศษแล้วจึงดึง value นั้นมาถ่วงรวม นั่นทำให้ความหมายของ token จากบริบทห่างไกลเชื่อมถึงกันได้โดยตรง
ตัวอย่างจากบทเรียนคือประโยค "อานนท์หยิบหนังสือจากโต๊ะ แล้วเปิดมัน" โดย token "มัน" จะได้คะแนนความเกี่ยวข้องสูงกับ token "หนังสือ" เนื่องจาก key ของคำนั้นสอดคล้องกับ query ของคำที่กำลังมองหา การสืบทอดความหมายนี้เกิดจากการเทียบเคียงของความคล้ายของป้าย ไม่ใช่การคำนวณระยะทางหรือตำแหน่งของคำนั้น
การคำนวณ query และ key ด้วย linear projection ที่ฝึกจากข้อมูลทำให้ระบบเรียนรู้ที่จะตั้งป้ายอย่างเหมาะสมได้ มันไม่ได้เรียนรู้ป้ายให้ตรงกับพจนานุกรม แต่เรียนรู้ที่จะจัดรูปแบบป้ายที่สะดวกกับการค้นค่าสความเกี่ยวข้องในครั้งถัดไป
**ตัวอย่าง — ประโยคตัวอย่าง**

"อานนท์หยิบหนังสือจากโต๊ะ แล้วเปิดมัน" — attention ช่วยให้ "มัน" รู้ว่าต้องดู "หนังสือ" แม้ห่างกัน 5 คำ โดย score จาก query ของ "มัน" ตรงกับ key ของ "หนังสือ" สูงสุด

## positional encoding และ multi-head attention

กลไก attention เทียบเฉพาะความคล้ายของเนื้อหาและตำแหน่งไม่ได้ จึงเป็นหน้าที่ของ positional encoding ที่จะให้ข้อมูลตำแหน่งที่ token อยู่ในประโยค ปัจจุบันมีหลายวิธีตั้งแต่ sinusoid ดั้งเดิมจนถึง relative positional หรือ RoPE ซึ่งให้ระบบรู้ว่า token ใดอยู่หน้าและหลังของ token ใด แม้เนื้อหาจะคล้ายกัน
Multi-head attention คือการรัน attention หลายชุดพร้อมกันโดยแต่ละหัวมี projection แยกกัน หัวแรกอาจเชี่ยวในเรื่องไวยากรณ์ อีกหัวอาจเชี่ยวในเรื่องอ้างอิงตำแหน่ง อีกหัวอาจดูตัวเลขและบริบทเชิงตัวเลข การรวมหลายหัวเป็นการขยายมุมมองในการเข้าใจความสัมพันธ์เชิงภาษาในครั้งเดียว
การออกแบบให้มีหลายหัวต้องโหลดข้อมูลให้สมดุลมาก เพราะหัวที่มีกำลังไม่เท่ากันอาจอุดกั้นหัวที่มีประโยชน์ วิธีบรรเทาคือการคำนวณทุกหัวใน parallel โดยไม่ใช้ข้อมูลของหัวอื่นก่อน และรวมผลลัพธ์ผ่านค่าเฉลี่ยงดุลสุดใหม่อีกครั้งก่อนนำไปทำขั้นตอนต่อไป

## ทำไมความซับซ้อนเป็น O(n²) และลดยังไง

Attention คำนวณคะแนนความเกี่ยวข้องระหว่างทุกคู่ของ token ซึ่งหมายความว่าเมื่อ prompt ยาวขึ้นงานที่ต้องทำจะเพิ่มกลายทวีคูณ เช่น เมื่อ prompt 100 token อาจมี 10,000 คู่ ส่วน prompt ยาว 1,000 token จะมี 1,000,000 คู่ นี่คือที่มาของเรื่อง O(n²) ที่เราพูดถึงในเรื่องประสิทธิภาพของ Transformer
เมื่อ prompt มีความยาวมากการคำนวณความเกี่ยวข้องระดับนี้จะช้าลงมากและใช้หน่วยความจำในปริมาณมากจนทำให้อัตราการเทรนและ inference ถดถอย หากใช้ prompt 128k token การคำนวณเชิงตรง ๆ แบบนี้จะกลายเป็นข้อจำกัดสำคัญจนเป็นไปไม่ได้ที่จะใช้โดยตรง
การประมวลผลให้เร็วขึ้นต้องยอมเสียความกว้างของความรู้ไปบางส่วน เช่น ใช้ windowed attention ที่ดูเฉพาะเพื่อนบ้าน หรือ sparse attention ที่กำหนดโครงสร้างการมอง ระบบล่าสุดอย่าง linear attention หรือ Mamba ลดความซับซ้อนให้เหลือระดับ O(n) แต่มักมี trade-off ในเรื่องความสามารถในการจับบริบทไกล

## decoder-only และการทำนาย token ถัดไป

โมเดลที่เราใช้กันในผลิตภัณฑ์คือ decoder-only ซึ่งถูกฝึกให้ทำนาย token ถัดไปจากการมองบริบทก่อนหน้าเท่านั้น ไม่ได้มองซ้ายขวาพร้อมกันเหมือน encoder รูปแบบนี้เหมาะกับการสร้างข้อความทีละ token เพราะการให้ตอบข้อความออกมาต้องต่อเนื่องกับสิ่งที่มาก่อนหน้าและต้องตอบอย่าง incremental
วัตถุประสงค์การเทรนคือ next-token prediction นั่นคือให้ข้อความนำหน้าทั้งหมดแล้วฝึกให้โมเดลเดา token ต่อไปได้อย่างแม่นยำ หลักการนี้เรียบง่ายแต่ให้แรงผลักดันแก่โมเดลในการเรียนรู้การเขียนและการทำตามรูปแบบที่ข้อความมักจะเป็นไปอย่างแม่นยำ
การออกแบบ decoder-only แบบนี้ทำให้การอนุมานต้องผลิตผลทีละตัวและต้องมี KV cache มาช่วยในภายหลัง แต่ข้อดีคือเป็นการออกแบบที่เข้ากับงานตอบสนองของมนุษย์ที่เกิดจากการคำนวณต่อเนื่องกัน เมื่อผู้ใช้เห็นข้อความตอบออกไปทีละคำระบบจะตอบได้แม่นยำมากขึ้น

## KV cache: ทำไม token แรกช้าแต่ token ต่อไปเร็ว

เมื่อสร้างผลลัพธ์ทีละ token เราจะไม่ต้องการ recompute attention ของ token เก่าอีกครั้งในทุกครั้ง เพราะจะทำให้งานซ้ำและช้าลงมาก วิธีแก้คือการแคช keys และ values ของทุก token ที่เคยผ่านมาแล้ว เรียกว่า KV cache เพื่อใช้ในการถ่วงความเกี่ยวข้องในรอบปัจจุบันโดยไม่ต้องคำนวณซ้ำ
แต่ KV cache คือหน่วยความจำที่โตตามความยาวของ context เพราะทุกครั้งที่มี token เพิ่มเข้าไปค่าที่ต้องเก็บจะเพิ่มขึ้นเช่นกัน การประมาณหน่วยความจำของ cache ปกติเป็นสองเท่าของ hidden จำนวน layer ต่อ token ต่อ batch และค่าไบต์ต่อค่าที่เก็บ กล่าวได้ว่าความยาวที่ใช้งานได้จริงถูกจำกัดโดย hardware มากกว่าตัวเลขในโมเดล
เหตุผลที่เห็นได้ชัดจากการใช้งานคือ token แรกที่ต้องประมวลต้องใช้เวลาในการ cache ค่าเดิมมากจึงทำให้ Time To First Token (TTFT) ช้ากว่า แต่ token ถัด ๆ ไปจะใช้เวลาสั้นกว่ามากเพราะเวลาที่ใช้ตอนนี้ได้ใช้ cache ที่มีอยู่แล้ว นั่นทำให้ inter-token latency สั้นกว่าตอนแรกอย่างมีนัยยะ
> [!TTFT]
> token แรกต้องอ่าน prompt ทั้งหมดและสร้าง cache รอบแรก จึงช้ากว่า token ถัด ๆ ไปที่แค่อ่าน cache ที่สร้างไว้แล้ว ข้อแตกต่างนี้คือเหตุผลที่ streaming output มักเร็วตั้งแต่ token ที่สองเป็นต้นไป
![Prefill processes the full prompt in parallel and fills the KV cache; decode appends one token at a time and memory grows linearly with sequence length](/diagrams/llm-loop.svg)

*Prefill vs decode and KV cache growth — Prefill ประมวล prompt ทั้งก้อนแบบขนาน (compute-bound) ส่วน decode สร้างทีละ token และอ่าน cache ทั้งก้อนทุกขั้นตอน (memory-bound) — cache โตเป็นเส้นตรงตามความยาว*
