## คำศัพท์ 3 ชั้นของ "การปรับ LLM"

SFT หรือ Supervised Fine-Tuning คือการเทรนต่อจาก pretraining ด้วยข้อมูลคู่ prompt กับ completion ที่คนเขียนหรือเลือกไว้ เป้าหมายคือเปลี่ยนรูปแบบตอบ เช่น ให้เป็นผู้เชี่ยวชาญ format หรือใช้ศัพท์เฉพาะ และจังหวะตอบที่แน่ชัด การฝึกเช่นนี้ทำให้โมเดลตอบตรงกับการใช้งานของทางธุรกิจได้ดีกว่า
instruction tuning และ alignment คือชั้นการฝึกเพิ่มเติมจาก SFT ซึ่งใช้ข้อมูลความคิดเห็นจากผู้ใช้และคำถามที่ต้องการให้ตอบตรงตามคำสั่ง เมื่อรวมกับ RLHF หรือ DPO ให้ระบบเรียนรู้ที่จะเลือกคำตอบตามความชอบแทนที่จะตอบไปเรื่อย ๆ กระบวนการนี้ทำให้เกิดความสามารถในการทำตามคำสั่ง ซึ่ง base model ไม่มี
ความเข้าใจที่สำคัญคือ fine-tuning ไม่ได้ทำให้โมเดลเรียนรู้ความรู้ใหม่โดยตรง แต่ปรับท่าทางการตอบอย่างเช่นรูปแบบการตอบและโทนการตอบ และเมื่อเราต้องการให้โมเดลอ้างข้อมูลจริงต้องใช้ RAG และ grounding เพราะการเทรนอย่างเดียวทำให้โมเดลตอบมั่นใจอย่างเดิมแต่ตามสไตล์ใหม่โดยที่ข้อมูลไม่ได้ดีกว่าเดิม
กล่าวโดยสรุป fine-tuning คือการเปลี่ยนสไตล์และรูปแบบการตอบให้ตรงกับทางธุรกิจ ซึ่งเหมาะเมื่อเรามี dataset ที่ครบถ้วนและสามารถระบุรูปแบบการตอบที่ต้องการได้ชัดเจน

## decision ladder: เลือกวิธีที่ประหยัดที่สุดก่อน

ลำดับขั้นของการตัดสินใจเริ่มต้นด้วย prompt และตัวอย่าง ซึ่งมีต้นทุนต่ำที่สุดและเปลี่ยนแปลงได้เร็วที่สุด การเริ่มที่นี่จะทำให้เห็นรอยร้าวของปัญหาได้ชัดกว่าการไปจ้างให้เทรนโมเดลโดยไม่รู้สาเหตุ เมื่อ prompt และตัวอย่างยังไม่สามารถทำงานที่ต้องการได้ขั้นต่อไปจึงพิจารณาการเปลี่ยนรูปแบบ
ขั้นต่อไปคือ retrieval และ RAG เมื่อข้อมูลมีความเปลี่ยนแปลงบ่อยและต้องการอ้างหลักฐานแหล่งที่มา ที่จะทำให้ไม่ต้องเทรนโมเดลใหม่และสามารถลบทิ้งจากระบบได้อย่างง่ายดาย ขั้นตอนนี้คือการแก้ปัญหาเรื่องความรู้และหลักฐานโดยตรงในหลายองค์กร
ขั้นตอนที่สามคือ fine-tuning เช่น SFT และ LoRA ซึ่งเหมาะกับงานที่ต้องใช้รูปแบบตอบ โทน และศัพท์เฉพาะให้คงที่ ไม่ว่าจะตอบเรื่องอะไร ขั้นตอนนี้ต้องใช้ dataset คุณภาพ 300 ถึง 1000 ตัวอย่าง หรือมากกว่านั้นเพื่อทำให้เทรนได้อย่างเสถียรและแน่นอน
ขั้นสุดท้ายคือ alignment ซึ่งเหมาะกับงานที่ต้องควบคุมการเลือกคำตอบตามความชอบ ซึ่งจะเกี่ยวข้องกับข้อมูลความคิดเห็นนั่นคือการใช้ duplicate control เพื่อให้ระบบตอบได้ตามความต้องการของธุรกิจอย่างชัดเจน แนวทางเลือกวิธีปรับโมเดลนี้ไม่ต้องไปเทรนทั้งหมดโดยไม่จำเป็น
> [!LADDER]
> ถามทุกครั้ง: ข้อมูลเปลี่ยนบ่อยไหม / ต้องอ้างหลักฐานไหม → RAG ก่อน; ปัญหาคือ format/โทน → prompt แล้วค่อย FT; ปัญหาที่ "วัดไม่ได้" → ไปแก้ eval ก่อนอย่าเพิ่งเทรน

## LoRA: เทรนเมทริกซ์เล็กแทนทั้งโมเดล

LoRA หรือ Low-Rank Adaptation แช่แข็ง weight เดิมและเพิ่มเมทริกซ์เล็กสองชุด ได้แก่ A และ B ที่ผลคูณช่วยประมาณการปรับของ weight ตลอดการเทรน เนื่องจากการปรับ LLM มักมี rank ต่ำทำให้เมทริกซ์เล็กสามารถจับการปรับได้ทำให้ประหยัด VRAM และสร้าง adapter หลายชุดสำหรับ checkpoint เดียวกันได้
ข้อดีของ LoRA คือลด parameter ที่ต้องเทรนอย่างมีนัยยะ จึงใช้ VRAM น้อยและยังสามารถเลือก adapter ที่ต้องการได้หลายชุดพร้อมกัน การรวม LoRA เข้าด้วยกันหรือ merge Adapter ต้องใช้ค่าที่กำหนดไว้ซึ่งจะต้องตัดสินใจอย่างละเอียดเพื่อให้ได้ข้อสรุปของการปรับที่ต้องการ
ข้อควรระวังคือถ้า rank มีค่าต่ำไประบบจะปรับได้จำกัดและถ้า rank สูงจะเปลืองทรัพยากร โดยใช้ rank ประมาณ 8 ถึง 64 แล้วปรับตามงาน actual เพื่อไม่ให้ค่านั้นกดความสามารถของ LoRA ไปมากเกินไปหรือเปลืองทรัพยากรที่เกินไป
ประเด็นที่เทรนด้วย LoRA ไม่ได้ให้ผลดีอย่างเดียวเสมอไป ต้อง validate ด้วย eval ที่ชัดเจนเพื่อยืนยันว่า LoRA ยังคงความสามารถในการเรียนรู้เช่นเดียวกับการประมาณทิศทางของผลเมทริกซ์ที่รวมในภายหลัง

## QLoRA และ quantization

Quantization คือการแปลง weight ของโมเดลให้กลับมามีขนาดเล็กลงด้วยการใช้ตัวเลขจำนวนน้อยกว่าเดิม ซึ่งช่วยประหยัด VRAM และคำนวณได้เร็วโดยไม่ต้องลดความสามารถของระบบอย่างเป็นนัยยะ quantization รูปแบบที่นิยมคือ 8-bit และ 4-bit ซึ่งทำให้โมเดลใหญ่ทำงานได้บนอุปกรณ์ที่มี VRAM จำกัด
QLoRA เป็นการรวม LoRA กับ quantization โดยใช้ base model ที่ quantize ในขณะที่เทรนด้วย LoRA adapter แนวทางนี้ช่วยประหยัด VRAM เพิ่มอีกขั้นหนึ่งและทำให้การเทรนโมเดลใหญ่เป็นไปได้ในระดับ consumer GPU โดยไม่สูญเสียความสามารถในการฝึกมากจนเกินไป
trade-off ของ quantization คือ precision loss ที่อาจเกิดขึ้นตามมา ทำให้คุณภาพภาคลดลง ข้อควรระวังคือต้องตรวจว่า precision loss ไม่ทำให้คุณภาพของผลลัพธ์ลดลงมากเกินไปโดยต้อง validate ด้วย eval ไม่ใช่เชื่อว่า quantization จะไม่มีผลอะไร
เมื่อ quantization และ LoRA ทำงานร่วมกัน การประเมินจึงจะเป็นสิ่งที่เสริมให้มีความมั่นใจในผลลัพธ์ไม่ใช่เพียงแนวคิดที่ว่า quantization เป็นสิ่งที่ทำได้เสมอไป

## ข้อมูลคุณภาพ กับสิ่งที่ "เทรนแล้วยังไม่ดี"

Fine-tuning ที่พังส่วนใหญ่มาจากข้อมูลที่ไม่ดีมากกว่าปัญหาเทคนิค สิ่งที่ทำให้เห็นได้ชัดคือชุดข้อมูลที่ไม่สอดคล้องกัน เกินขนาด ไม่ครบคลุมทั้งงานหรือมีสไตล์ที่แตกต่างกัน ทำให้เทรนได้ผลที่ไม่สอดคล้องและถ้าชุดข้อมูลยังเล็กหรือไม่ครอบคลุมยังคงล้าสมัยและไม่ดีพอสำหรับการเทรน
การตรวจสอบข้อมูลเริ่มจากเขียน guideline ที่ชัดเจนแล้วตรวจความสอดคล้องด้วย LLM ร่วมกับมนุษย์ หลังจากนั้นเราจะสร้าง test set ที่แยกออกมาโดยไม่ให้ overlap กับการเทรนเพื่อให้ผลลัพธ์ที่ได้จะเป็นผลการเทรนจริง ดังนั้นการเตรียมข้อมูลจึงเป็นพื้นฐานที่ดีที่สุดก่อนเทรน
วิธีเตรียมที่ดีที่สุดคือการสร้าง dataset ที่มีความสอดคล้องกันและเขียน guideline ที่ชัดเจนเพื่อให้ dataset นั้นสามารถปรับให้ดีได้และเทรนได้อย่างแน่ชัด ไม่เช่นนั้นจะทำให้ระบบเม้มจำ train set แต่ validation กลับแย่ลงเพราะการฟิตเกินไป หรือเรียกอีกอย่างว่า overfitting
การที่ fine-tuning ชนะ prompt จริงไม่ใช่ว่าโมเดลจะดีกว่าในอ้อมแขนทุกเกม แต่ชนะในกรณีที่ prompt และ RAG ยังทำไม่ได้เพราะปัญหาของ format และศัพท์ การเทรนจึงควรมี eval ที่จับสิ่งที่ prompt แก้ไม่ได้อย่างชัดเจนแทนการเทรนแบบไม่รู้จุดมุ่งหมาย

## ต้นทุนการตัดสินใจ: รวมผมไม่ใช่แค่ GPU

เมื่อตัดสินใจว่าจะ fine-tune เราต้องมองต้นทุนครบทุกมิติ ไม่ใช่เพียงแค่ GPU เพราะเวลาที่มนุษย์เสียไปในการเก็บ dataset, เขียน guideline, ตรวจข้อมูลและ calibrate ต้นทุนเหล่านั้นเป็นชิ้นส่วนใหญ่และไม่ควรถูกมองข้ามในการเปรียบเทียบกับทางเลือกอื่น
เมื่อเราเทรนแล้วต้องใช้เวลากับเงินในการเทรน และการประเมินบ่อยครั้ง ดังนั้นต้นทุนจริงจึงสัมพันธ์กับจำนวนรอบของการเทรนและการตรวจสอบ ในขณะที่การแก้ไข prompt อาจใช้ plugin module ง่าย ๆ โดยลดต้นทุนการทำงานได้ชัดเจนกว่าการเทรนโมเดลใหม่
เมื่อโมเดลพร้อมออกสู่ production ต้องค่าใช้จ่ายในเรื่องของ maintenance adapters ที่เหล่านั้น และเวลาใช้งานอุปกรณ์ที่มี latency และ maintenance ต้องถูกนำมาพิจารณาด้วยเพราะการเปลี่ยนโมเดลโดยตรงอาจไม่เป็นผลดีเพราะยังคงมีความทับซ้อนและขั้นตอนที่ต้องควบคุม
กล่าวโดยสรุปตัดสินใจที่จะ fine tune ควรใช้ eval ที่บ่งบอกถึงสิ่งที่ prompt แก้ไม่ได้ และเมื่อข้อมูลพร้อมแล้วจึงค่อยพิจารณาโมเดลใหม่ การไม่พิจารณาต้นทุนครบทุกมิติจะทำให้ตัดสินใจผิดและเสียทรัพยากรไปโดยเปล่าประโยชน์
