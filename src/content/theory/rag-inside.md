## RAG แก้ปัญหาอะไร และสถาปัตยกรรมคร่าว ๆ

LLM ที่ตอบจากความรู้เดิมอย่างเดียวโดยไม่มีข้อมูลภายในองค์กรหรือข้อมูลที่อัปเดต จะเสี่ยงตอบเก่าและขาดหลักฐาน การเลื่อนโมเดลไปใช้การอ่านเอกสารโดยตรงแทนการตอบจากความจำอย่างเดียวเป็นการเปลี่ยนหน้าที่ของโมเดลจากผู้ตอบรัว ๆ มาเป็นผู้อ่านเอกสารก่อนตอบซึ่งแก้ปัญหาได้ระดับหนึ่ง
pipeline ของ RAG ประกอบด้วย ingest เอกสาร แบ่งเป็น chunk สร้าง embedding แล้วเก็บใน index ขั้นตอนค้นหาจะดึง chunk ที่เกี่ยวข้องกับคำถาม หลังจากนั้นจะส่ง chunk นั้นกลับไปให้โมเดลและสั่งให้ตอบโดยอ้าง chunk นั้นแทนการตอบจากความจำ เพราะแบบนี้โมเดลไม่ต้องรู้ทุกอย่างแต่แค่อ่านจากแหล่งที่โยงกลับไปหาได้
ความสำคัญของ RAG ไม่ใช่การทำให้โมเดลเก่งขึ้นแต่เปลี่ยนงานของโมเดลจากจำและเดามาเป็นอ่านจากหลักฐานแทน เมื่อเอกสารดึงมาไม่ถูกต้อง prompt ดีแค่ไหนก็ช่วยอะไรไม่ได้ ข้อจำกัดของการค้นหาจึงเป็นตัวกำหนดคุณภาพของคำตอบสุดท้ายโดยตรง
กล่าวโดยสรุป RAG ไม่ใช่เพียงการเชื่อม tool เข้ากับ LLM แต่คือการออกแบบว่าข้อมูลในระบบจะดึงเข้าสู่ context อย่างไรและจะอ้างอิงอย่างไร นั่นคือโครงสร้างที่สำคัญที่สุดของระบบนี้
> [!DEBUG ORDER]
> ตรวจครั้งแรกที่ retrieval (พบเคสไหม) → ต่อด้วย context (เคสนั้นไปอยู่ใน prompt หรือไม่) → แล้ว generation (ตอบตามเคสนั้นหรือร่างความ) — อย่าโทษ prompt ตั้งแต่ทีแรก
![Offline chunk, embed, and vector database; online hybrid retrieve, cross-encoder rerank, then LLM generation with citations or a no-answer refusal](/diagrams/rag-pipeline.svg)

*RAG pipeline: chunk to generate — Offline: chunk + metadata → embed → vector DB. Online: hybrid retrieve → rerank (cross-encoder) → generate แบบอ้าง chunk id — ไม่มีหลักฐานต้องปฏิเสธ ไม่ใช่เดา*

## ingest: นำเอกสารเข้า index และล้างข้อมูลเก่า

ขั้นตอนแรกของระบบคือการ ingest เอกสารซึ่งหมายถึงการอ่านเอกสารทั้งหมดที่ผู้ใช้ต้องใช้อ้างอิงแล้วแปลงเป็นไฟล์ที่พร้อมค้นหา การทำความสะอาดข้อมูลและการลบเนื้อหาซ้ำซ้อนเป็นส่วนสำคัญที่มักถูกมองข้าม และการทำงานในช่วงเริ่มต้นจะทำให้คุณภาพของ index โดยรวมดีกว่าเมื่อใช้ข้อมูลเก่าหรือข้อมูลซ้ำ
เมื่อเอกสารมีการปรับแก้ จะต้องลบ vector เก่าและเก็บ vector ใหม่ลงใน index เสมอ เพราะข้อมูลที่ค้างอยู่จะทำให้ระบบดึงของเก่าและวัดออกมาไม่ถูกต้อง ขั้นตอนนี้เป็นงานเบื้องหลังที่ทำให้ RAG เชื่อถือได้เมื่อการปรับแก้เอกสารเกิดบ่อย
การวัด ingest ที่ดีคือการดูแลสัดส่วนที่เก็บข้อมูลว่าเป็นเนื้อหาที่ใช้งานได้โดยตรงและไม่เสียความเป็นหนึ่งเดียวของข้อมูล แต่ละเอกสารต้องมีตัวบ่งชี้ source id และเลขหน้าเพื่อให้ citation อ้างอิงกลับและปรับให้สอดคล้องกับระบบค้นหา

## Chunking และ metadata: ของดีต้องมี "ป้ายกำกับ"

chunking คือการแบ่งเอกสารให้เป็นชิ้นเล็ก ๆ ที่จัดการได้ ขนาดเริ่มต้นที่เหมาะกับหนังสือหรือเอกสารยาวส่วนใหญ่คือ 300 ถึง 600 token และมี overlap 10 ถึง 15 เปอร์เซ็นต์เพื่อให้ได้ทั้งการเทียบเคียงผลลัพธ์และการซ้อนสายความหมายใน Chunk ที่อยู่ติดกัน นอกจากการเลือกขนาด chunk แล้วเราต้องรักษาหัวข้อในเอกสารโดยการแบ่งตามหัวข้อและย่อหน้าเพื่อให้ไม่ตัดกลางประโยค
metadata คือข้อมูลเพิ่มเติมของทุก chunk เช่น source id เลขหน้า หัวข้อ วัน ส่วน แผนก หรือหน่วยงานของเอกสาร ข้อมูลเหล่านี้คือเครื่องมือกรองคำค้นในภายหลังและใช้ในการแสดง citations การขาด metadata ทำให้ระบบไม่สามารถกรองคำค้นตามสิทธิ์และขอบเขตของเอกสารได้
metadata สำคัญพอ ๆ กับเนื้อหาเพราะใช้ลดขอบเขตการค้นในชั้น filter ก่อน rerank ใช้แสดง citation ให้ผู้ใช้เห็นแหล่งที่มาจากเอกสารและตรวจสอบว่าเอกสารที่อ้างความเป็นจริง แต่ก็ไม่จำเป็นเสมอไปที่จะใส่ metadata มากเกินไปเพราะจะทำให้ระบบซับซ้อนและเป็นการเปลืองเวลาที่ไม่เกี่ยวข้อง

## การค้นที่ใช่ ไม่ใช่แค่ "embedding อย่างเดียว"

การค้นหาในงานจริงมักเป็นการรวมกันของ dense embedding และ BM25 วิธีแรกเห็นความหมายได้แต่เสี่ยงกับคำหายาก วิธีที่สองจับคำที่หายากได้คือ keyword ตรง ๆ จึงไม่มีจุดอ่อน การรวมกันด้วยการทำ weighted sum หรือ Reciprocal Rank Fusion (RRF) ช่วยให้ได้ candidate ที่สมบูรณ์และมีความหลากหลายของความหมาย
เมื่อ candidate เหล่านี้ถูกนำไปสืบค้นแล้วเราจะ rerank ด้วย cross-encoder เพื่อเลือกจำนวนที่ในที่สุดจะเข้ากับ context การ rerank ด้วย cross-encoder ให้ผลตอบที่แม่นกว่าเป็นการใช้ vector เปรียบเทียบอย่างเดียวเพราะเป็นการเปรียบเทียบทั้งคำถามและคำตอบโดยตรง ไม่ใช่เพียงเวกเตอร์ที่ถูกสรุปมาครึ่งเดียว
แม้แต่ระบบที่ดีที่สุดก็ยังต้องระวังเรื่องตำแหน่งของ candidate ใน context และการเลือกตำแหน่งที่จะเก็บข้อมูลถาวร เพราะตำแหน่งนี้มีผลต่อการวิเคราะห์ของ next token สำหรับงานที่ต้องการการค้นคำตอบระยะใกล้ ควรทำความเข้าใจกับการทำงานของโมเดลก่อนแล้วจึงค่อยตัดสินใจเมื่อพบช่องโหว่

## synthesis: บังคับ citation และ "ไม่มีคำตอบ"

ในขั้นตอน synthesis ต้องสั่งให้โมเดลอ้างอิง chunk id จริงที่อยู่ใน context และตรวจว่าคำอ้างแต่ละอย่างอ้าง chunk id ที่มีอยู่จริงหรือไม่ภายในโค้ด ทั้งนี้โมเดลไม่ได้อ้างถูกเองโดยอัตโนมัติเสมอไปจึงต้องมีการตรวจสอบให้แน่ใจก่อนตอบอย่างที่ต้องการจากระบบ
การมีเส้นทาง no-results คือการตอบเรื่องที่ไม่มีข้อมูลในเอกสารโดยตอบว่าไม่มีในเอกสารแทนการเดา วิธีนี้ลด hallucination และทำให้ผู้ใช้รู้ว่าข้อมูลไหนไม่ได้อยู่ในทรัพยากร เพราะเป็นการให้ทางเลือกที่เป็นจริงมากกว่าการเดาผลลัพธ์
เทคนิคเสริมที่ทำให้ระบบมี grounded มากขึ้นคือการตัดและจัดเรียง context ก่อนใส่เข้า prompt ไม่ให้โมเดลสรุปเกินขอบเอกสารและเพิ่มขั้นตอนตรวจสอบหลังหาคำตอบว่าคำตอบนั้นได้รับการสนับสนุนจากหลักฐานจริงหรือไม่ ซึ่งมีสามระดับคือ grounded, partial และ ungrounded

## วัด RAG แยกส่วนเพื่อรู้ว่าต้องแก้ตรงไหน

ระบบ RAG ที่พังมักมีสาเหตุที่แยกได้ชัดเจนเพียงแค่มองภาพรวมได้ยาก วัดเพียงคำตอบสุดท้ายอย่างเดียวจึงไม่รู้ว่าสิ่งที่ผิดคือขั้นตอนใด ดังนั้นจึงต้องแยกวัด retrieval quality, context relevance และ generation faithfulness ออกจากกันอย่างชัดเจนแล้วดูว่าจุดที่ผิดคือขั้นใดในการประเมินว่าระบบทั้งหมดทำงานได้จริงหรือไม่
เราต้องคำนวณ recall@k ซึ่งบอกว่าเอกสารที่ถูกอยู่ใน k อันแรกหรือไม่และประเมิน context relevance ในทุก candidate ว่าเคสที่ดึงมาใช้ตอบได้จริงมีกี่เคส และ generation faithfulness บอกว่าคำตอบที่ให้อ้างหลักฐานจริงแล้วแค่ไหน การแยกแบบนี้ทำให้เราเห็นสาเหตุของความล้มเหลวแต่ละอย่างได้ชัดเจน
การตั้งรายงานเป็น trace คือการบันทึกลำดับ query, retrieved chunks, final answer ไว้เป็นสายเพื่อการดูย้อนหลังได้ทีละขั้น เพราะตัวเลขเฉลี่ยเชิงสถิติซ่อนจุดที่ผิดเฉพาะเจาะจงที่เป็นเอกสารหรือรูปแบบใด การทบทวน trace นี้จะทำให้เห็นข้อบกพร่องที่มองไม่เห็นจากตัวเลขเฉลี่ย
