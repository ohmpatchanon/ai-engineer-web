## สามชุดข้อมูลที่ห้ามปนกัน: train, validation, test

ข้อมูลแบ่งออกเป็น 3 ส่วน: train ใช้ปรับพารามิเตอร์, validation ใช้ตัดสินใจปรับ hyperparameter (learning rate, ขนาดโมเดล) ระหว่างเทรน และ test ใช้ประเมินครั้งเดียวตอนจบเพื่อไม่ให้เกิด "การลอบเล่น" กับชุดประเมิน — เพราะถ้าเรากลับไปปรับโดยดู test ซ้ำแล้วซ้ำเล่า test ก็จะกลายเป็น train อีกชุด ตัวเลขสวยขึ้นแต่โลกจริงไม่เปลี่ยน
กฎเหล็ก: ถ้าจะทดสอบหลาย ๆ แนวคิด ให้ใช้ validation ตัดสิน แล้วใช้ test แค่ครั้งเดียวสุดท้าย ถ้าจำเป็นต้องดู test ซ้ำ ต้องยอมรับว่าค่าที่รายงานไม่ใช่ค่าที่ตรงกับสภาพจริงอีกต่อไป ทุกครั้งที่เราตัดสินบน test ค่าที่ได้จะคุยกับ "ความน่าจะเป็นที่ดีสุดของสุ่มชุดทดสอบ" มากขึ้น
การแบ่ง 80/20 นั้นง่ายแต่ไม่ได้เป็นธรรมเสมอ ข้อมูลไม่ดุล (เช่น fraud 0.1%) ถ้าแบ่งสุ่มอาจทำให้ test สุดปรับ้วนไม่มี fraud เลย โมเดลจะดูแม่นโดยไม่เคยเจอเคสสำคัญ การแบ่งที่คำนึงถึงสัดส่วน (stratified split) และมิติเวลา/กลุ่มเป็นสิ่งที่ลดความหลงนี้ และการเลือกวิธีแบ่งต้องดูจากลักษณะของงาน
ประเด็นที่คนพลาดมากสุดคือ การคำนวณสถิติของข้อมูลทั้งชุดก่อน split เช่น หา mean ของคอลัมน์แล้วใช้ไป normalize ข้อมูลทั้งชุด นี่คือการ "มองเห็นอนาคต" ของชุด test ตั้งแต่ยังไม่ split เพราะสถิตินั้นคำนวณจากตัวอย่างที่รวมชุด test ไว้ด้วย ทำให้ค่าที่ได้ใน lab สูงกว่าค่าจริง
trade-off ของการ lock test แบบเข้มงวดคือ เสียโอกาสเรียนรู้จากข้อมูลบางส่วนที่ test แตะได้ แต่การยอมรับขอบเขตนี้คือต้นทุนของการประเมินที่เชื่อถือได้ หากไม่ lock จะได้ตัวเลขสวยแต่คำตอบ deployment ไม่ตรงกับดอกข้อมูลจริง
> [!RULE]
> validation = ตัดสินใจระหว่างเทรน, test = วัดผลจริงครั้งเดียว ใช้ test ซ้ำ = โกงตัวเอง

## confusion matrix: นับจำนวนผิดที่คิดว่าไม่สำคัญ

metric พื้นฐานที่สุดของงาน classification คือ confusion matrix ที่ตาราง 2x2: TP (ทาย positive และถูกจริง), FP (ทาย positive แต่ไม่ใช่ — เตือนเท็จ), FN (ปล่อยผ่านของจริง — พลาด), TN (ทาย negative และถูก) ตารางนี้บอกทุกอย่างที่จำเป็นสำหรับวิเคราะห์ต้นทุน เพราะแต่ละช่องอาจมีความต้นทุนไม่เท่ากัน
Precision คือสัดส่วนที่ทายว่า positive มีจริงกี่ส่วน สูตร: TP/(TP+FP) ใช้เมื่อ false positive แพง (เช่น เตือนภัยเท็จ ทำให้คนรำคาญและเสียความเชื่อถือ) Recall คือสัดส่วนของจริงที่จับได้ สูตร: TP/(TP+FN) ใช้เมื่อ false negative แพง (เช่น คัดโรคพลาดทำให้ผู้ป่วยถูกปล่อยไป) ทั้งสองตำแหน่งบอกมุมมองคนละด้านของโมเดล
F1 score เป็น harmonic mean ของ precision และ recall รวมให้เป็นตัวเลขเดียว และยังมีวิธีวัดแบบ PR-AUC ที่ดูในหลาย threshold พร้อมกัน F1 ดูสมดุลดีแต่ชักชวนให้ความรู้สึกว่าคแหลมอัน ทั้งสองmetric ต้นทุนเท่ากันทั้งที่งานจริงต้นทุนต่างกันเสมอ ดังนั้นเมื่อต้องตัดสินใจ deployment ให้รู้ว่ามา metric ตัวไหนเลือกครั้งใช้คะแนน และความหมายของตัวเลือกนี้อะไร
ตัวอย่างจริง: spam filter ที่ precision 99% แต่ recall 50% จะ "ไม่รบกวน" แต่ปล่อยสแปมเข้าอีเมลครึ่งหนึ่ง ขณะที่ระบบเตือนการฉ้อโกงที่ recall สูงแต่ precision ต่ำจะก่อภาระสอบสวนเท็จจำนวนมาก การเลือก metric จึงต้องกลับไปที่คำถามเดียว: ผิดแบบไหนแพงกว่า
trade-off ตรงนี้คือ โมเดลที่เปลี่ยน threshold จะปรับ balance ระหว่าง precision/recall ได้เสมอ เวลาใส่โมเดลขึ้นอีเมลจริงต้องเริ่มจากโจทย์ธุรกิจก่อน แล้วค่อยปรับ threshold ให้เหมาะสมกับตลาด ไม่ใช่เลือก threshold ที่ accuracy สูงที่สุดแล้วค่อยปรับแบบย้อนหลัง
### สูตร: Precision vs Recall และ F1

Precision = TP/(TP+FP)   ·   Recall = TP/(TP+FN)   ·   F1 = 2 × (P × R) / (P + R)

> Precision ถาม "ที่บอกว่าใช่ ใช่จริงแค่ไหน" / Recall ถาม "ของใช่ทั้งหมด จับได้กี่ส่วน" — เลือกตามฝั่งที่แพงกว่า. F1 คือค่าเฉลี่ยฮาร์มอนิกสมดุล ไม่ได้แทนต้นทุนจริงทุกกรณี
```python
from sklearn.metrics import confusion_matrix, precision_score, recall_score, f1_score

# y_true: 0=ลบ, 1=บวก ; y_pred: โมเดลทาย
y_true = [1, 0, 1, 1, 0, 0, 1, 0]
y_pred = [1, 0, 1, 0, 0, 1, 1, 0]

print(confusion_matrix(y_true, y_pred))  # [[TN FP],[FN TP]]
print('precision', precision_score(y_true, y_pred))
print('recall', recall_score(y_true, y_pred))
print('f1', f1_score(y_true, y_pred))
```

## ROC-AUC ใช้เมื่อไร และใช้ผิดเมื่อไร

ROC-AUC วัดความสามารถแยกสองคลาสของโมเดลในทุก threshold อย่างเดียว ค่า 0.5 = เดาสุ่ม 1.0 = แยกสมบูรณ์ เป็น metric ที่นิยมนึกถึง แต่มัน "ไม่บอก" ว่าที่ threshold ที่คุณจะใช้จริง (เช่น ป้ายว่า fraud เมื่อคะแนน > 0.7) ประสิทธิภาพจริงเป็นอย่างไร และข้อมูลไม่สมดุลมาก ๆ (เช่น fraud 0.1%) ROC-AUC อาจดูสูงโดยที่โมเดลใช้ไม่ได้เลย — เพราะ class ใหญ่ (ปกติ) ครอบงำการคำนวณ
ทางเลือกที่เหมาะกับข้อมูลไม่สมดุลคือ PR-AUC และที่สำคัญที่สุดคือดูตัวเลขจริงที่ threshold ใช้งานจริง: precision, recall, และ confusion matrix ของ threshold นั้น เล็กน้อยแต่สำหรับการตัดสินใจ deployment มันเป็นข้อมูลที่ ROC-AUC ให้นึกภาพไม่ออก
ความแตกต่างที่สำคัญคือ accuracy กับ AUC ไม่ได้วัดสิ่งเดียวกันเลย accuracy ตอบว่า "เดาถูกกี่เปอร์เซ็นต์ในข้อมูลชุดนี้" (แต่โดน class ใหญ่กลบหมด) ส่วน AUC ถามว่า "แยกสองคลาสเก่งแค่ไหนในทุกจังหวะ threshold" ดังนั้นโมเดลที่ accuracy 99% ในชุดที่ 99% คือคลาสลบ อาจแยกคลาสบวกไม่ออกเลย AUC ต่ำ
trade-off หนึ่งที่ต้องเข้าใจคือ ความถนัดในการอธิบายโมเดล (เช่น โมเดลที่ให้คะแนนสอบตามอายุ) นั้นสำหรับกลุ่มประชากร ไม่ใช่กับเมื่อข้อมูลกลุ่มเดียวหรือ เมื่อเอา AUC ของกลุ่มใหญ่มาอธิบายโมเดลสำหรับกลุ่มยี่สิบเปอร์เซ็นต์ที่ปัจจุบันนั้น สัดส่วนกลุ่มก็อาจเปลี่ยนผล
กฎการใช้งานตอนมาตรฐานคือ ใช้ AUC เป็น metric แบบหนึ่งในการปรับจูนโมเดล เปรียบเทียบสองโมเดลพร้อม threshold คงที่ ส่วนตอนตัดสินใจจะ deploy ใช้ precision/recall/F1 ที่ threshold จริงเท่านั้นและต้องวินิจฉัยช่อง confusion matrix ดูเสมอ

## metric สำหรับ regression มองเห็นภาพต่างจาก classification

งาน regression วัดมูลค่าที่ต่อเนื่อง เช่น ราคาบ้าน, ยอดขาย, หรือคะแนนความเสี่ยงแทนการแบ่งเป็นใช่/ไม่ใช่ metric หลักคือ MAE (Mean Absolute Error = เฉลี่ยค่าสัมบูรณ์ของความผิด), RMSE (Root Mean Squared Error = นำความผิดยกกำลังสองแล้วถอดราก), และ R² (สัดส่วนความแปรปรวนที่อธิบายได้) แต่ละตัวตอบคำถามคนละมุม
MAE กับ RMSE ต่างกันที่วิธีลงโทษความผิด: MAE ค่าเฉลี่ยแบบเส้นตรงให้ความอดทนต่อค่าผิดปกติ (outlier) มากกว่า ส่วน RMSE ยกกำลังสองทำให้ความผิดใหญ่ลงโทษหนักกว่ามาก หากโจทย์ต้องการหลีกเลี่ยง big error (เช่น การทำนายราคาของชิ้นส่วนที่อันตรายเมื่อพลาดมาก) เลือก RMSE มากกว่า ส่วนการต้องการภาพรวมแบบไม่สับสนกับ outlier เลือก MAE
R² บอกได้ว่าโมเดลอธิบายได้กี่เปอร์เซ็นต์ของความแปรปรวน เช่น R² = 0.70 หมายความว่าโมเดลสสารข้อความ 70% ของความแปรปรวนในข้อมูล แต่เหมือนกับ accuracy ใน classification R² ที่สูงไม่ได้หมายความว่าค่าที่ทำนายลงตัวทุกจุด อาจมีค่ากลางผิดมากแต่สองปลายดี ฯลฯ คุณต้องดู MAE/RMSE คู่กันเสมอ
ตัวอย่าง: โมเดลทำนายรายได้จากอายุ (regression) ถ้า MAE = 5,000 หมายความว่าโดยเฉลี่ยพลาดที่ ±5,000 บาท อันนั้นเข้าใจได้เลยและใช้ประเมินว่า error ดีพอไหมกับงบของโจทย์ ดีกว่าแค่การโชว์ R² 0.80 การคำนึงถึง error gap ในหน่วยงานจริงทำให้เข้าใจว่าตัวเลขนั้นซื้อข้อจำกัดได้แค่ไหน
trade-off ที่ต้องเผชิญคือ overlap ของโมเดลที่ใช้ metric ที่ดีที่สุดสามารถซ่อนจุดอันตรายในงานจริง เช่น ทำนายค่าความเสี่ยงที่ RMSE ดี แต่เมื่อค่าเสี่ยงสูงจริงกลับทำนายต่ำจะอันตรายกว่า โจทย์บางข้อต้องการปรับ loss ให้เหมาะกับผลกระทบจริง (weight ที่ต้นทุก state)
### สูตร: Metric หลักงาน regression

MAE = (1/n) Σ |ŷ − y|   |   RMSE = √((1/n) Σ (ŷ − y)²)   |   R² = 1 − SS_res / SS_tot

> ŷ=ค่าที่ทำนาย, y=ค่าจริง, SS_res=ผลรวมกำลังสองของสิ่งที่เหลือ, SS_tot=ความแปรปรวนทั้งหมดของค่าจริง

## cross-validation, กลุ่มข้อมูล และเวลา: วิธีแบ่งที่ซื่อสัตย์

k-fold cross-validation แบ่งข้อมูลเป็น k ส่วน วนใช้แต่ละส่วนเป็น validation โดยมีส่วนอื่นเป็น train แล้วเฉลี่ยผล — ลดผลกระทบของ "โชคดี/โชคร้าย" จากการแบ่งครั้งเดียว และใช้ข้อมูลเต็มที่เหมาะกับชุดข้อมูลขนาดกลาง
ข้อควรระวังที่คนพลาด: ห้ามใช้ cross-validation เป็น "test ชุดใหม่" เพื่อหลอกตัวเองว่าไม่เคยดู test — ข้อมูล 20% ที่ split ออกมาต้องไม่ถูกแตะตอนพัฒนาเลย (holdout test) การใช้ k-fold ครบชุด 100% เพื่อเลือก hyperparameter แต่ละครั้ง เท่ากับดู test ไปแล้วโดยอ้อม
สำหรับข้อมูลที่มี dimension ที่ segment ข้อมูล (เช่น ผู้ใช้ same คน, หรือหลายบทสนทนา) ต้อง split ตามกลุ่ม (group split) เพื่อไม่ให้ข้อมูลของคนเดียวกันโผล่ทั้งสองฝั่ง และสำหรับข้อมูลเวลา/อนุกรมเวลาต้อง split ตามเวลา (temporal split) เพราะในชีวิตจริงข้อมูลอนาคตไม่เคยอยู่ในอดีต ถ้า split สุ่มจะได้ตัวเลขสวยเฉพาะที่เพราะข้อมูลซ้อนทับ
อีกจุดที่พลาดบ่อยคือ การจับค่าสถิติรวมทั้งชุดก่อนการ split เช่น การทำ target encoding หรือการ scale ตามค่าที่เก็บจากข้อมูลทั้งหมด ก็คือเลื่อนการรั่วเข้ามาเหมือนของที่เก็บจาก test การ fit ต้องทำภายใน train เท่านั้น และการใช้ cv ในขั้นตอนกลางก็ต้องถูกต้องตามลำดับเดียวกัน
trade-off ของ CV คือ ใช้ข้อมูลเต็มที่และประเมินเสถียรภาพได้ดี แต่ใช้เวลามากกว่า split ครั้งเดียวเมื่อจำนวน fold และงานใหญ่หลายเท่าตัว หลักปฏิบัติคือ ใช้ CV เมื่อข้อมูลเล็ก/ต้องการประเมินความเสถียร และใช้ single split เมื่อข้อมูลใหญ่พอที่จะวัดได้ชัดแบบไม่ต้องสำรวจเพิ่ม
```python
# CV กับการแบ่งตามกลุ่มและเวลา
from sklearn.model_selection import StratifiedKFold, GroupKFold, TimeSeriesSplit

# ข้อมูล वर्गจัดคลาสไม่สมดุล
skf = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)
```

## data leakage: ตัวเลขสวยที่สุดคือตัวเลขที่หลอกที่สุด

Leakage คือข้อมูลจาก "อนาคต/คำตอบ" รั่วเข้าไปในการเทรน ทำให้โมเดลดูเก่งใน lab แต่พังในโลกจริง ตัวอย่างคลาสสิก: ลบ out-of-stock รายการออกจาก train เท่านั้นโดยไม่ลบจาก test, นำ target ไปใช้สร้าง feature, หรือใส่สถิติรวมทั้งชุด (เช่น mean ของคอลัมน์) ลงใน feature ที่คำนวณข้ามแถว — เฉลี่ยทั้ง train+test ก่อน split เป็นต้น
รูปแบบที่พบใน RAG/LLM คือสอบถามด้วยชุดคำถามที่โมเดลเคยเห็นตอน pretrain หรือมีเนื้อหาต้นฉบับอยู่ในคำตอบ — ทดสอบต้องใช้วัสดุที่ "ไม่อยู่ในคลังความรู้ของโมเดล" จริง ๆ เลือกข้อมูลใหม่ (temporal) หรือคนเขียนใหม่จากเนื้อหาอื่น
Leakage ในเชิงข้อมูล (data leakage) มักเกิด 5 รูปแบบ: (1) การคำนวณสถิติทั้งชุดก่อน split, (2) feature ที่เกี่ยวข้องกับคำตอบระหว่างทดลอง (future information), (3) ข้อมูลซ้ำใกล้เคียง (near-duplicate) ข้ามชุด train/test, (4) target หรือ proxy ของ target รั่วเป็น feature, (5) กลุ่มข้อมูล (เช่น ผู้ใช้เดียวหลายแถว) แยกไม่ครบ
วิธีจับง่ายที่สุด: split ตามเวลา (หรือกลุ่ม) อย่างเคร่งครัด แล้วเช็คว่า validation ลดลงมากจาก split แบบสุ่มหรือไม่ — ถ้าลดฮวบ แสดงว่า split สุ่มกำลัง "ให้โชค" ด้วยการรั่ว เลือกวิธีแบ่งข้อมูลจะต้องมาจากงานจริงก่อนเสมอ แล้วระดับของรั่วจะเดาไม่ได้เมื่อเริ่มจากค่า supposing ชัด
trade-off ของการแก้ leakage คือ เสียความเสถียรเมื่อเล่นเทคนิคเล็กน้อยกับข้อมูลแค่บางส่วน และต้องออกแบบ pipeline ที่ป้องกันการ fit ข้ามชุดข้อมูล เพราะต้องให้ห้องเรียนจริงเที่ยงตรง ถ้าไม่ยอมเสียค่าใช้จ่ายตรงนี้ทุกครั้ง จะได้โมเดลที่สร้างภาพสวยแต่ใช้จริงไม่ได้
**ตัวอย่าง — กรณีที่จับได้ยาก**

โมเดลทำนายสัญญาเลิกจ้าง ฝึกบนข้อมูลปี 2020-2023 แล้ว split test แบบสุ่ม ทำให้คน 30% ใน test เกิดก่อน 2020 — โมเดล "รู้" ผลลัพธ์ของคนเหล่านี้จากการเทรนเพราะข้อมูลซ้อนกัน วิธีแก้: split ตามเวลา (คนเกิด/ข้อมูลหลังจุดตัดใช้ได้เท่านั้น) เสมอสำหรับข้อมูลอนุกรมเวลา
> [!TIP WHEN METRIC สวยเป็นธรรมชาติ]
> accuracy 99% ในงานยาก (เช่น แยกหมวดโรค 5 ชนิด) คือสัญญาณที่ต้องสงสัย leakage ก่อนที่จะฉลองความสำเร็จ — ให้ตรวจ duplication และ feature ที่ใกล้ target ก่อน

## ออกแบบการทดลองและปรับ threshold ที่ทำให้ผลไม่หลอก

การเทียบสองโมเดลอย่างเป็นธรรมด้วยวิธี single metric ที่สุ่มอาจไม่มากพอสำหรับกรณีที่ความต่างน้อย (เช่น เปลี่ยนโมเดลใหม่แต่ metric เดิมอาจไม่มี test อีกอันหนึ่งต้องใช้สถิติยืนยัน) ดังนั้นเมื่อทำ A/B test ทดสอบจะต้องใช้ test set ขนาดใหญ่พอและมีสัดส่วนคลาสถูกต้อง เพื่อให้มั่นใจว่าความต่างที่เห็นไม่ใช่เสียงรบกวน
อีก trade-off ที่ชวนให้เกิด confusion คือการปรับ threshold บน validation แทน test เพื่อให้แล้วกับ metric ตัดสินใจไม่เป็นธรรมต่อโมเดลก่อนเวลา thresholds ใหญ่แต่ threshold ที่เลือกบนชุดข้อมูลชุดไหนจะต้องเตรียมไว้แล้วกำหนดล่วงหน้าในเอกสารทดลอง
การเลือก metric จากต้นทุนของคำตอบสามารถทำได้ตั้งแต่ก่อนเริ่มเทรน เช่น เมื่อ cost ของ false positive สูงกว่า false negative 5 เท่า ต้องล็อกเป็นโจทย์การเลือก metrics ตั้งแต่ต้น ไม่ใช่หลังเทรนเป็นหลังหวังว่า metric ใดดีที่สุดแล้วค่อยจะดึงออกมาในงานจริงและจะไม่ทำให้เราเพิกถอนข้อจำกัดและการทดลอง
นอกจากนั้นการเทรนซ้ำหลาย ๆ ครั้งโดยเลือก threshold ที่ผ่าน validation ตอนนั้น แต่ test เซตนั้นชุดทดสอบแรกอื่นจะ give ไม่ได้ (ความผันผวนสูง) จะทำให้สรุปผลผิด การแก้คือกำหนดกติกาและทำซ้ำ ยืนยันการทดลองอย่างจำกัดจำนวนครั้งและบันทึกทุกการทดลองไว้
ลุยให้การทดลองซื่อสัตย์มากขึ้นเรื่อย ๆ อาจมีค่าใช้จ่ายเพิ่ม (ข้อมูล test ใหม่, ทีมตรวจสอบภายนอก) แต่ข้อดีนั้นคุ้มความเสี่ยงที่จะหลงเข้าสู่การขายโมเดลที่ดูสวยมากแต่ใช้ในตลาดไม่ยืนได้

## เช็คลิสต์ก่อนรายงานตัวเลขและก่อน deploy

- split ก่อนทุกอย่าง: แยก test ออกทันทีหลังเก็บข้อมูล แล้ว lock ไว้
- มีการ split ตามเวลาหรือตามกลุ่มผู้ใช้ หากข้อมูลมี dimension เวลา/กลุ่ม
- ระหว่าง develop ใช้ train/validation เท่านั้น ห้ามดู test
- เลือก metric จากต้นทุนของธุรกิจก่อนเทรน ไม่ใช่หลังเห็นผล
- สุดท้าย รัน test หนึ่งครั้ง รายงานค่า พร้อม record seed ของการทดลอง
- ตรวจ leakage: หา duplicate, target-derived feature, future feature ก่อน deploy
- รายงาน confusion matrix / MAE และขนาดชุด test ไม่ใช่แค่ accuracy เดี่ยว ๆ
