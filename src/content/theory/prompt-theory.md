## Prompt คือ สัญญา ไม่ใช่คาถา

Prompt ไม่ได้ทำให้โมเดลฉลาดขึ้น เพราะโมเดลจะไม่ได้ความรู้ใหม่อย่างฉับพลันแต่การบอกถึงงานที่ต้องการจะทำให้โมเดลเข้าใจว่าจะใช้ความรู้แบบไหนกับขั้นตอนใดจึงจะออกมาดีที่สุด แนวคิดของ prompt จึงไม่ได้เป็นการเปลี่ยนความฉลาด แต่เป็นการชี้ให้โมเดลเลือกมุมมองที่เหมาะสมกับงาน
prompt ที่ดีคือสัญญาที่ชัดเจนที่มีโครงสร้างของงาน ขอบเขตของการตอบ และตัวอย่างที่ชัดเจนซึ่งผู้ใช้จะต้องกำหนดไว้กับผู้ใช้ปลายทาง โดยใช้ Role, Task, Context, Format, Example, Criteria เพราะนี่คือส่วนประกอบที่ทำให้โมเดลรู้ได้ว่าจำเป็นต้องทำอะไรและจะตรวจผลนั้นได้อย่างไร
การมอง prompt ในฐานะสัญญาทำให้เราออกแบบเพื่อทดสอบผลแทนการรู้สึกว่ามันดีเพราะตัวเลขที่ง่ายต่อการวัดและทำ progress ในทุกขั้นตอนได้ เมื่อทุกคำใน prompt ชัดเจนก็จะทำให้การทดสอบเป็นไปได้ง่ายขึ้นและการตัดสินใจนั้นได้ผลลัพธ์ที่วัดได้จริง
นี่คือเหตุผลว่าทำไม prompt ที่สั้นแต่ครอบคลุมงานจึงดีกว่า prompt ยาวที่คลุมเครือ ดังนั้นจึงควรออกแบบ prompt ให้คลุมไว้ทุกมิติที่จำเป็นสำหรับงานแต่ไม่เกินความจำเป็นที่ต้องใช้
```text
คุณคือผู้ตรวจสัญญา
งาน: สกัดคู่สัญญาเป็น JSON
ข้อจำกัด: ห้ามเดา; ถ้าไม่มีค่าให้ null; ใช้ ISO date
รูปแบบผลลัพธ์: {"party": string|null, "value": number|null, "date": string|null}
ตัวอย่าง: "สัญญาระหว่าง A และ B มูลค่า 250,000 บาท ลงนาม 12 มี.ค. 25" → {"party":"A และ B","value":250000,"date":"2025-03-12"}
เกณฑ์: ค่าทุกตัวต้องมีหลักฐานในข้อความต้นฉบับ
```

## few-shot กับ chain-of-thought ทำงานอย่างไร

few-shot คือการให้ตัวอย่าง 2 ถึง 5 คู่ input-output อย่างชัดเจน มันไม่ได้สอนความรู้ใหม่แก่โมเดลแต่ทำหน้าที่เหมือนการส่งสัญญาณว่า output ต้องออกมาในรูปแบบใดและอยู่ในขอบเขตใด นั่นทำให้คำตอบที่โมเดลออกมานั้นมีมาตรฐานและมีความสม่ำเสมอมากขึ้นอย่างมีประสิทธิภาพ
chain-of-thought คือการให้โมเดลคิดออกมาเป็นขั้น ๆ เมื่อต้องการให้ระบบคำนวณหลายขั้น ผลลัพธ์จะดีขึ้นมากจากความคืบหน้าในทุกก่อน เพราะโมเดลจะสามารถเห็นความคิดของตัวเองและใช้มันในการตัดสินใจในขั้นถัดไปได้ดีกว่าการตอบทันทีโดยไม่มีขั้นตอน
ข้อแลกเปลี่ยนของ chain-of-thought คือ token จำนวนมากและ latency ที่เพิ่มขึ้น เพื่อให้โมเดลได้ทำการคำนวณ ในหลายงาน zero-shot เพียงพอและได้ผลที่เหมือนกันและเร็วกว่ามาก ทางที่ดีจึงเป็นการทดสอบก่อนว่าฝ่ายไหนคุ้มกับการใช้งานที่สุด
มุมมองในทางปฏิบัติคือ few-shot และ chain-of-thought ไม่ใช่กลยุทธ์ของนักมายากล แต่เป็นกลไกที่ส่งผลเชิงระบบและการกำหนด prompt ต้องคู่ไปกับการออกแบบ eval เพื่อควบคุมความสม่ำเสมอและวัดผลลัพธ์ที่เปลี่ยนไป
> [!NOT A TRICK]
> Few-shot/CoT เปลี่ยนพฤติกรรมเก่งได้ แต่อย่าเอาไป "ใช้เป็นเคล็ดลับ" โดยไม่รู้กลไก — prompt ที่ดีต้องเข้าคู่กับ eval ที่วัดว่างานเปลี่ยนจริง

## role, context และขอบเขตของงาน

Role เป็นการบอก persona ให้โมเดล ซึ่งช่วยบอกท่าทีและขอบเขตของการตอบแต่ไม่ได้เปลี่ยนความรู้ที่โมเดลมี การเลือกใช้ Persona ที่ชัดเจนเช่น ผู้ตรวจสัญญาหรือผู้สรุปข้อมูลจะทำให้การตอบนั้นตรงตามบทบาทที่เราต้องการ
Context คือข้อมูลที่อยู่ในงานทั้งหมดที่เป็นประโยชน์รวมทั้งภูมิหลังของงานและข้อความที่เกี่ยวข้อง สิ่งเหล่านี้มาช่วยให้โมเดลเข้าใจรายละเอียดและตัดสินใจเลือกมุมมองที่เหมาะสมกับงานได้มากขึ้น
ข้อจำกัดและเกณฑ์ในการตัดสินเป็นส่วนที่ต้องระบุไว้เสมอเช่น ห้ามเดา ถ้าไม่มีคำตอบ ต้องคืนค่า null หรือใช้ภาษาที่เป็นกลางอย่างชัดเจน เมื่อตัวเลือกเหล่านี้ชัดเจน prompt จะไม่ได้กลายเป็นข้อความคลุมเครือแต่กลายเป็นสัญญาที่ตรวจผลได้

## structured output และการให้สัญญาที่ตรวจได้

การสั่งให้ส่งออก JSON อย่างเดียวไม่ได้ทำให้ได้ JSON ที่ถูกต้องเสมอไป เพราะยังมีโอกาสที่โมเดลจะใส่ข้อความนอกเหนือรูปแบบหรือเขียน syntax ไม่สมบูรณ์ การทำให้ JSON ที่ถูกต้องจึงต้องมีการระบุ schema อย่างชัดเจนและให้ตัวอย่างอีกหนึ่งคู่ไว้ด้วย
อีกวิธีที่ทำได้จริงคือการใช้ function/tool calling ซึ่งบังคับโครงสร้างของผลลัพธ์โดยตรงผ่าน API นั่นทำให้ผลลัพธ์ออกมาในกรอบที่เราต้องการก่อนส่งต่อได้ ข้อแลกเปลี่ยนคือ cost ของการเรียก API และความซับซ้อนของโค้ด
วงจร retry หลังการ validate ความถูกต้องของ JSON หมายความว่าเราจะมีโครงสร้างของ downstream ที่มั่นคงและไม่ต้องพึ่งโมเดลแต่เพียงอย่างเดียว อีกการกำหนดทางคือการตรวจจับและแยก "ยังไม่รู้คำตอบ" ไว้โดยกำหนดค่า null แทนการเดา ซึ่งเป็นสิ่งที่ทำให้ระบบมีความเปิดเผยและเชื่อถือได้
ผลเชิงโครงสร้างที่ชัดเจนนี้สำคัญมากสำหรับงานเช่นระบบบันทึกข้อมูลหรือ DB ที่ต้องการ schema แน่นอน การออกแบบสัญญา output จึงเป็นส่วนหนึ่งของสถาปัตยกรรมระบบ ไม่ใช่เพียงการเขียน prompt เท่านั้น

## prompt ที่ทดสอบได้คือ prompt ที่ version ได้

ปฏิบัติที่ดีที่สุดคือการเก็บ prompt ลงใน repository เป็นไฟล์และทำชุด test อย่างเป็นทางการเพื่อรัน eval ทุกครั้งที่แก้ prompt เพราะ prompt แก้เพียงเล็กน้อยอาจทำให้ผล regression ในงานโดยรวมได้ วิธีนี้การเปลี่ยนแปลงของ prompt กลายเป็นงานที่วัดผลได้มากกว่าการรู้สึกว่าดีขึ้น
สร้าง golden set ขนาด 30 ถึง 50 เคสจากงานจริงและรัน eval ทุกครั้งที่เปลี่ยน prompt ตัวเลขนี้นี้คือสิ่งที่ทำเพื่อให้ความถูกต้องสำหรับการยืนยันว่าการแก้ prompt นั้นดีขึ้นจริง ไม่ว่าจะใช้โมเดลเดิมหรือเปลี่ยนโมเดลก็ตาม
สิ่งที่ทำให้ prompt เปราะมากที่สุดคือการเปลี่ยนโมเดล เมื่อโมเดลเปลี่ยน การตีความคำเดียวกันอาจเปลี่ยนไปอย่างมีนัยยะ จึงต้องระบุ prompt นี้ปรับกับโมเดลใดและซิงค์ไว้ให้เสมอเพื่อความปลอดภัยในการเปรียบเทียบ

## ข้อจำกัดของ prompt engineering เมื่อเทียบกับระบบใหญ่

prompt engineering คงช่วยปรับทิศทางของโมเดลได้ แต่ไม่ได้เปลี่ยนจุดประสงค์หลักของโมเดลและไม่ได้แก้ข้อจำกัดพื้นฐานจากการฝึกเดิมของมัน การคาดหวังให้ prompt จะแก้การ hallucination ในระดับระบบได้เป็นความคาดหวังที่เกินขอบเขตของความสามารถของ prompt
เมื่อต้องใช้ระบบที่ต้องมีการจัดการหลายขั้นตอนเช่น retrieval และการเรียนรู้ความแตกต่างระหว่างคำในข้อความก็เป็นเรื่องของการออกแบบสถาปัตยกรรมมากกว่าการปรับ prompt อย่างเดียว การมุ่งแต่ปรับ prompt จะมาถึงขีดจำกัดอย่างรวดเร็วในขณะที่สถาปัตยกรรมยังไม่เหมาะสม
ดังนั้นการใช้ prompt ควรอยู่ภายใต้การควบคุมด้วย eval ที่ชัดเจน และต้องรู้ว่าจุดใดต้องเปลี่ยนไปเป็นการปรับ architecture หรือ fine-tuning แทน เมื่อการปรับ prompt ไม่สามารถทำให้ผลตอบดีขึ้นได้
